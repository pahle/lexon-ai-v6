Status: implementation and Checkpoint A are ready for main's scoped rerender and

### TDD, rendering, and integration evidence

- RED: the Compose onboarding browser assertion measured `main` at 616px on a
  1440px viewport. After adding the full-width sizing, the next assertion exposed
  an empty `Display name` input despite the profile API returning the seeded
  value `Checkpoint Preview`.
- GREEN: `AuthFrame` fills the flex parent; the real browser check now asserts
  main width equals both viewport widths and the display-name input is 320px at
  desktop and mobile. It also asserts the actual input value before capture.
- Next client/server source inspection: the installed Next 16.4.3 client builds
  `/_next/hmr`; `server/lib/router-server.js` matches that same route and passes
  the request through `blockCrossSiteDEV`. The server was started with hostname
  `0.0.0.0`, while Playwright opened the app at `http://127.0.0.1:<published
  port>`. The HMR request had matching browser origin and Host at that port,
  but Next's default dev-origin list does not include `127.0.0.1`. In
  visual-dev-only config, `allowedDevOrigins: ['127.0.0.1']` now permits that
  loopback origin; production config is unchanged. The browser sees the matching
  `ws://127.0.0.1:<published port>/_next/hmr` client URL and a WebSocket 101
  handshake. The seeded input then contains the exact API-returned profile name.
- Visual dev now emits a small test-only auth-form readiness marker from the
  mounted sign-in/sign-up client component. The e2e helper waits for that marker
  before interacting or capturing those forms; onboarding instead waits for the
  actual seeded input value. No DOM value is faked and no auth handler/policy is
  changed.
- The unchanged F1 end-to-end flow reaches successful UI signup and email
  verification (`POST /api/auth/sign-up/email` 200, verify endpoint 302). Its
  subsequent browser sign-in request is observed as `POST
  /api/auth/sign-in/email`, but the browser receives no response event or
  `Set-Cookie`, and no identity request follows. The test ends on
  `/sign-in?returnTo=%2Fworkspace`. This remains an unresolved visual-dev
  sign-in integration finding; the response is absent, so no session/guard
  cause is claimed. Keep the unchanged flow as a production verification gate
  after Task 5 restores the full build.
- Exact visual checkpoint command:

  ```sh
  LEXON_VISUAL_DEV=1 pnpm test:e2e -- --project visual-review
  ```

  Expected coverage is sign-in/up captures, authenticated incomplete onboarding
  captures, 1023/1024 cover geometry, and six secondary account routes. Main
  owns final rerender, side-by-side comparison, and acceptance; this task does
  not claim that review.
