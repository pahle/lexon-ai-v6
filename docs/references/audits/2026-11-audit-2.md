## What is solid

- **RLS.** Every `app` table has ENABLE and FORCE. Every `lexon_app` policy uses the `NULLIF(current_setting('app.org_id', true), '')::uuid` form, and the chat tables add `app.user_id` owner binds. All 15 `USING (true)` policies are `TO lexon_migrator` only (for example `0026_chat_tree.sql:35,38,65,108`, `0027_chat_owner_fence_fixes.sql:93-99`, `0033_chat_cleanup.sql:24,50,77,82`, `0035_chat_search.sql:26-27`). Every `SECURITY DEFINER` function that `lexon_app` can execute compares its arguments to the `app.*` GUCs.
- **Authorization.** `TenantGuard` is global and defaults to `workspace` access (`tenant.guard.ts:44`). It rejects tenant-override headers and body keys (`:55-69`). Platform routes require the admin role, MFA, and re-authentication (`organization-auth.port.ts:48-69`). No route that should need authentication was found without it. The only public routes are `/api/health*`, `/api/identity/admin-setup/redeem` (rate-limited) and the allowlisted public Better Auth endpoints.
- **Error and log hygiene.** Client errors carry only fixed codes and messages (`error.filter.ts:117-182`, `identity-access/auth-output.ts`). Logs are rebuilt from an allowlist (`infrastructure/telemetry/logging.ts:26-63,105-154`).
- **Cross-tenant HTTP tests exist** for chat get, list, search, rename, feedback, stop, run SSE, sessions, identity reads, members, settings and invitations (B-01 lists the gaps).
- **Replay bound.** Stream `MAXLEN` is at most 1024 (`0015_ai_engine.sql`, `CHECK (max_len BETWEEN 1 AND 1024)`), so the fixed `XRANGE … COUNT 1024` (`queue/sse-stream-reader.ts:103-109`) cannot truncate a replay. A reader lead to the contrary was refuted.

## Findings

### B-01: Six chat routes have no HTTP cross-user or cross-organization negative test

- **Severity:** Important. **Theme:** 1 (tenancy: read paths without cross-tenant tests).
- **Evidence:** these `ChatController` routes (`backend/src/modules/chat/chat.controller.ts`) are never called by another user, or by a user from another organization, in any integration or E2E test:

  | Route                                                    | Line   | What exists instead                                                                       |
  | -------------------------------------------------------- | ------ | ----------------------------------------------------------------------------------------- |
  | `POST /api/chats/:chatId/search-match/:messageId` (read) | `:166` | only same-owner cases: deleted, stale and branch (`chat-search.spec.ts:322,393,423`)      |
  | `DELETE /api/chats/:chatId`                              | `:204` | only the owner (`chat-delete.spec.ts`; no second identity)                                |
  | `POST /api/chats/:chatId/messages`                       | `:214` | single user only (`chat-send.spec.ts`, 4 tests)                                           |
  | `POST …/messages/:messageId/edit`                        | `:227` | "foreign" means the same user's other chat (`chat-branches.spec.ts:101-129`, expects 409) |
  | `POST …/messages/:messageId/regenerate`                  | `:245` | same as edit                                                                              |
  | `PUT /api/chats/:chatId/viewed-leaf`                     | `:283` | same owner only (`chat-branches.spec.ts:334-345`)                                         |

  Sibling routes do have such tests: `chat-rename.spec.ts:94`, `chat-feedback.spec.ts:91-92`, `chat-stop.spec.ts:277`, `chat-api-privacy.spec.ts:115,175`, `chat-search.spec.ts:537-543`, and `chat-sse.spec.ts:947`.

- **Cause:** the F4 tests grew one route at a time. The same-org peer test (`chat-api-privacy.spec.ts:175`) covers only `GET`. Enforcement today is `withTenant` plus the owner-bound RLS policies (`0026_chat_tree.sql:20-33,98-105`). No leak was found. But nothing at the HTTP layer would catch a regression, for example a repository call that builds its scope from the URL instead of the actor. Send, edit and regenerate start AI runs, so a regression there would run a model on another user's conversation.
- **Violates:** LEX-ARC-001 §3.2 item 3 (line 177): "CI runs negative cross-tenant and cross-project tests for every read path (API, worker, retrieval, SSE, export)". `search-match` is a read path. The write routes are covered by the brief-level "owner-only" rule.
- **Suggested fix:** none in the product. Add the tests.
- **Test to add:** one integration spec, for example `chat-cross-actor.spec.ts`. For each of the six routes, call it with (a) a same-organization peer and (b) a member of another organization, using a real chat id and message id from the owner. Expect the same safe 404 body that a random id gets. Also assert no side effect: no new `ai_runs` row, no outbox row, unchanged `viewed_leaf_id`, and the chat still present.

### B-02: Every live text delta costs two tenant DB transactions and about six Valkey round trips, awaited serially

- **Severity:** Important (a performance and reliability hot path; not measured). **Theme:** 4.
- **Evidence:**
  - `chat/step-executor.ts:1247-1267` awaits `#publishCursor` for **every** model `text-delta` (and reasoning delta, `:1150-1177`) inside the model-stream loop. Nothing coalesces the deltas.
  - `queue/run-streams.ts:173-241` (`publishWithCursor`) calls `#serverDeadline` (Valkey `TIME`) and then `#publishPart` for each part.
  - `#publishPart` (`:503-575`) does `GET` epoch, `#activeProof`, `EXISTS`, `ZSCORE`, `#activeProof` **again** (`:553`), the `#prepare` eval, and the append eval.
  - `#activeProof` calls `authority.authorizeActive`, which is a full `withTenant` transaction (`bootstrap/ai-worker-providers.ts:67-71`: `BEGIN`, two `set_config`, `SELECT`, `COMMIT`).
  - The deadline is 250 ms (`run-streams.ts:129,181`). When a publish misses it, the executor sets `streamFramingAvailable = false` and `streamSnapshotRequired = true` (`step-executor.ts:1263-1265`). The rest of the attempt is then delivered only through checkpoints and the tree poll.
- **Cause:** fencing correctness was designed per event: each part re-proves the claim against PostgreSQL. Per token that means about 2 DB transactions plus about 7 Valkey round trips, serialized with the provider stream. At worker concurrency 4 and roughly 30–60 deltas/s per run, that is about 250–500 DB transactions/s from streaming alone. When the database is slow, the live stream degrades to snapshot mode instead of shedding load.
- **Why the evidence does not cover it:** the F4.2 S2 burst measured SSE admission, first-frame latency and auth-pool wait (`F4.2-acceptance.md` Gate 6.5). It did not measure per-delta publish latency, or how often runs fall back to snapshot mode, under real token rates.
- **Suggested fix (smallest safe):**
  - Coalesce deltas in the executor: flush every N ms (for example 50 ms) or every M bytes, so one publish carries many tokens. The AI SDK UI stream accepts larger `text-delta`s.
  - Within one publish, reuse the first `#activeProof` unless the registry reconcile path ran. The second proof at `:553` exists only for that path.
  - Record a counter of snapshot-mode fallbacks per run (K3).
- **Test to add:** yes.
  - A unit test with a fake model that emits 200 one-character deltas: assert at most ⌈duration/flush⌉ publishes, and at most one `authorizeActive` per publish when no reconcile happens.
  - An integration test: with a 150 ms injected DB delay per transaction, a 200-delta answer still streams live (no `streamSnapshotRequired`).

### B-03: A-02 partly holds: exhausted serialization retries return 500, and `ECONNREFUSED` is labelled an auth outage

- **Severity:** Minor. **Theme:** 2 (error paths).
- **Evidence:**
  - `identity-access/organization-auth.port.ts:104-111`: on `attempt === 2` a `40001`/`40P01` is rethrown raw, and the `throw new IdentityError('AUTH_UNAVAILABLE', 503)` at `:111` is still unreachable. `SafeErrorFilter` has no branch for `40001`/`40P01` (`error.filter.ts:17-26,151-181`), so the client gets **500 `INTERNAL_ERROR`**. `organizations.spec.ts:369-372` asserts the raw `cause: { code: '40001' }` at the service layer, which pins this behaviour.
  - `error.filter.ts:22-26,85-94,157-162`: any error in the cause chain whose message contains `ECONNREFUSED`, or whose code is `ECONNREFUSED`, becomes 503 `AUTH_UNAVAILABLE` "Authentication is temporarily unavailable." That includes the app pool and Valkey (ioredis), for example in chat routes. The frontend then shows an authentication outage for a chat dependency failure.
- **Cause:** the A-02 fix moved mapping into the filter but left the port's retry loop unchanged. The "unavailable" predicate is not tied to the dependency that failed.
- **Suggested fix:**
  - In the port, map an exhausted `40001`/`40P01` to `IdentityError('AUTH_UNAVAILABLE', 503)` and delete the dead line. Alternatively, add `40001`/`40P01` to `UNAVAILABLE_SQLSTATES`.
  - Use a neutral code (`SERVICE_UNAVAILABLE`) for non-auth routes, or decide the label from the route's module.
- **Test to add:** yes.
  - An HTTP-level test: three injected serialization failures (`organization-fixture.ts:96` already supports this) return 503 `AUTH_UNAVAILABLE`.
  - A filter unit test: an ioredis `ECONNREFUSED` on a chat route does not produce an auth-labelled body.

### B-04: A-07 partly holds: the poll abort never reaches the network, and each tick reloads the whole tree

- **Severity:** Minor. **Theme:** 4.
- **Evidence:**
  - `chat/use-tree-polling.ts:53-58` passes a fresh `AbortSignal` to `fetchTree`.
  - `chat-runtime.tsx:202-204` (`refreshTree(signal)`) calls `onTreeRefresh()` **without** it.
  - `chat-view.tsx:94-97` (`refreshActiveTree`) calls `client.get(chatId)` without a signal, and `chat-client.ts:78` `get` takes no signal at all (`list` and `search` do, `:79-93`).
  - The abort therefore only drops the result. On unmount or a hidden tab, the request still runs for up to the 10 s client timeout (`chat-client.ts:36-37`).
  - Each tick runs `ChatMessageRepository.tree` (`infrastructure/db/chat-message.repository.ts:280-311`). That query loads every message of every branch, with `final_output` of every run, a feedback join, and a `LATERAL` checkpoint lookup per row. There is no row limit and no chat size cap: no message limit exists in `backend/src` or `shared/src`.
  - The poll runs at 1 s while urgent (`chat-runtime.tsx:262-265`, which includes "until the first stream frame").
- **Cause:** A-07 changed cadence, pausing and error surfacing, but not the transport of the request. The safety-net poll still uses the full read model.
- **Suggested fix:** add `signal?: AbortSignal` to `ChatClient.get` and thread it through `onTreeRefresh(signal)`. Later, a light `GET /api/chats/:id/status` (active run id, run status, version) could drive the poll, with the full tree fetched only on a change.
- **Test to add:** yes. In `chat-runtime-poll.spec.tsx`, unmounting during an in-flight poll aborts the `fetch` (`init.signal.aborted === true`).

### B-05: Run streams still re-authorize every second per stream

- **Severity:** Minor. **Theme:** 4 (SSE hot path; the remainder of A-04).
- **Evidence:** `chat/run-events.service.ts:413-474`. Every run-stream connection renews its lease every 1000 ms (`:458-474`) and then calls `checkAuthorization()`. The cache key is `(user, run, channel, session)` with a 1 s TTL (`:417-437`), and each miss runs:
  - `#revalidate`: a session assert on the auth pool, single-flight per `(user, session, org)` with a 1 s TTL (`:132-138`);
  - **plus** an `existsForOwnedChat` `withTenant` query (`:424-429`).

  So each open run stream costs about one app-pool transaction per second, and each session about one auth-pool transaction per second. The invalidation stream uses 5 s (`:38,330`). The F4.2 burst evidence recorded an auth-pool wait p95 of 2488 ms and a peak of 269 pool waiters (`F4.2-acceptance.md`, Gate 6.5 table).

- **Cause:** A-04's interval change was applied to `/api/chats/events` only.
- **Suggested fix:** use `REVALIDATION_INTERVAL_MS` (5 s) for run streams too. Revocation is already pushed by deletion and cancel signals. Keep the 1 s lease renewal.
- **Test to add:** yes. A fake-timer unit test in `run-events-revalidation.spec.ts`: over 10 s, one run stream causes at most 2 session asserts and 2 ownership queries.

### B-06: Security and authority tests that still accept any rejection

- **Severity:** Minor. **Theme:** 3 (tests that would pass on broken code).
- **Evidence:** each of these would also pass on a DB outage, a TypeError, or an unrelated exception.
  - `backend/test/integration/provisioning.spec.ts:54-61`: a platform staff member cannot create a team (`organizations.create(...)` `.rejects.toThrow()`). This is an authorization boundary.
  - `backend/test/integration/ai-privacy-audit.spec.ts:98-119`, "auth transaction writer cannot append AI audit authority": bare `.rejects.toThrow()`. The test just above it checks the message (`:90`).
  - `backend/test/integration/chat-fence.spec.ts:252-277`, "a chat-bound run cannot remove its declared resource to escape the fence": `.rejects.toThrow()`, followed by `expect(await fixture.chat.tree(0, chat.id)).toBeDefined()`. That read-back is vacuous: `tree` returns `null` or a tree, and `null` is defined. The resource list itself is never read back.
  - `backend/test/unit/request-identity.spec.ts:71`: `.rejects.toBeDefined()`.
  - Lower risk, because a state read-back follows: injected-failure rollback tests such as `departure-audit.spec.ts:113`, `admin-setup.spec.ts:306`, `invitations.spec.ts:440`, `own-sessions.spec.ts:130,133`, `personal-organization.spec.ts:46`, `provisioning.spec.ts:229`, and `chat-title.spec.ts:655,756`.
  - Frontend: `chat-transport.spec.tsx:1535,1684` assert `streamError` `toBeDefined()` without its type or code. The request counts after them still discriminate.
- **Cause:** A-16 fixed the tests it listed but added no rule against bare rejections.
- **Suggested fix:**
  - Assert the code: `ORG_FORBIDDEN` or `AUTH_FORBIDDEN` for provisioning, the SQLSTATE (`42501`) or the trigger message for the audit and fence cases, and the error class for request identity.
  - In `chat-fence`, read back `resolved_config.resourceIds` and expect it unchanged.
  - Optionally, add an ESLint `no-restricted-syntax` rule for `.rejects.toThrow()` with no argument and for `.rejects.toBeDefined()` in `backend/test/integration`.
- **Test to add:** yes (tighten the tests listed). For each one, prove the new assertion fails with a deliberately wrong expected code, as F4.2 did for A-16.

### B-07: The RLS catalog test covers only ordinary `app` tables; the `ops` K3-only rule is not pinned

- **Severity:** Minor. **Theme:** 1 and 3.
- **Evidence:**
  - `backend/src/infrastructure/db/testing/rls-fixture.ts:50,67,80,112` filter `n.nspname='app' AND c.relkind='r'`. A partitioned table (`relkind='p'`) or a view in `app` would escape the catalog check. None exists today: `PARTITION BY` and `CREATE VIEW` do not appear in `backend/drizzle`.

The job envelope is validated (`parseJobEnvelope`), but no test asserts that an `ops` table has no K1-capable column, or that every outbox payload type is ids-only.

  - Add an `ops` inventory test: enumerate the `ops` tables and their `jsonb`/`text` columns against an explicit allowlist, so a new K1-capable column fails CI. Also assert every registered outbox type's Zod schema has only id, enum and number fields.
