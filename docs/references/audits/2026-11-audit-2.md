## Findings

### B-01: Six chat routes have no HTTP cross-user or cross-organization negative test

- **Severity:** Important. **Theme:** 1 (tenancy: read paths without cross-tenant tests).
- **Evidence:** these `ChatController` routes (`backend/src/modules/chat/chat.controller.ts`) are never called by another user, or by a user from another organization, in any integration or E2E test. Each spec that calls them was checked for a second identity:

  | Route                                                    | Line   | What exists instead                                                                                                                            |
  | -------------------------------------------------------- | ------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
  | `POST /api/chats/:chatId/search-match/:messageId` (read) | `:166` | only same-owner cases: deleted, stale and branch (`chat-search.spec.ts:322,393,423`)                                                           |
  | `DELETE /api/chats/:chatId`                              | `:204` | same identity only (`chat-delete.spec.ts`, `chat-delete-races.spec.ts`); `chat-api-privacy.spec.ts:94-107` tests cross-origin, not cross-actor |
  | `POST /api/chats/:chatId/messages`                       | `:214` | single user only (`chat-send.spec.ts`, 4 tests)                                                                                                |
  | `POST …/messages/:messageId/edit`                        | `:227` | "foreign" means the same user's other chat (`chat-branches.spec.ts:101-129`, expects 409); each test there has one identity                    |
  | `POST …/messages/:messageId/regenerate`                  | `:245` | same as edit                                                                                                                                   |
  | `PUT /api/chats/:chatId/viewed-leaf`                     | `:283` | same owner only (`chat-branches.spec.ts:334-345`)                                                                                              |

  Sibling routes do have such tests: `chat-rename.spec.ts:94`, `chat-feedback.spec.ts:91-92`, `chat-stop.spec.ts:277`, `chat-api-privacy.spec.ts:115,175`, `chat-search.spec.ts:537-543`, and `chat-sse.spec.ts:947`.

- **Cause:** the F4 tests grew one route at a time. The same-org peer test (`chat-api-privacy.spec.ts:175`) covers only `GET`. Enforcement today is `withTenant` plus the owner-bound RLS policies (`0026_chat_tree.sql:20-33,98-105`). No leak was found. But nothing at the HTTP layer would catch a regression, for example a repository call that builds its scope from the URL instead of the actor. Send, edit and regenerate start AI runs, so a regression there would run a model on another user's conversation.
- **Violates:** LEX-ARC-001 §3.2 item 3 (line 177): "CI runs negative cross-tenant and cross-project tests for every read path". `search-match` is a read path; the write routes fall under the briefs' owner-only rule.
- **Suggested fix:** none in the product. Add the tests.
- **Test to add:** one integration spec, for example `chat-cross-actor.spec.ts`. For each of the six routes, call it with (a) a same-organization peer and (b) a member of another organization, using the owner's real chat id and message id. Expect the same safe 404 body that a random id gets. Also assert no side effect: no new `ai_runs` row, no outbox row, unchanged `viewed_leaf_id`, and the chat still present.

### B-02: Every live text delta costs two tenant DB transactions and about six Valkey round trips, on an undersized pool

- **Severity:** Important (a performance and reliability hot path; not measured). **Theme:** 4.
- **Evidence:**
  - `chat/step-executor.ts:1247-1267` awaits `#publishCursor` for **every** model `text-delta` (and reasoning delta, `:1150-1177`) inside the model-stream loop. Nothing coalesces the deltas.
  - `queue/run-streams.ts:173-241` (`publishWithCursor`) calls `#serverDeadline` (Valkey `TIME`), then `#publishPart` for each part.
  - `#publishPart` (`:503-575`) does `GET` epoch, `#activeProof`, `EXISTS`, `ZSCORE`, `#activeProof` **again** (`:553`), the `#prepare` eval, and the append eval.
  - `#activeProof` calls `authority.authorizeActive`, which is a full `withTenant` transaction (`bootstrap/ai-worker-providers.ts:67-71`: `BEGIN`, two `set_config`, `SELECT`, `COMMIT`).
  - **Pool versus concurrency:**
    - The AI worker runs up to 4 interactive plus 2 batch jobs (`infrastructure/queue/queue-consumer.ts:44-45`).
    - Every runtime shares one app pool of `DATABASE_POOL_MAX` = 5 (`config/runtime-config.ts:23`, `docker-compose.yml:26`, `.env.example:15`).
    - Its acquire timeout is 5000 ms (`infrastructure/db/tenant-database.ts:44`), far above the 250 ms publication deadline (`run-streams.ts:129,181`).
  - When a publish misses the deadline, the executor sets `streamFramingAvailable = false` and `streamSnapshotRequired = true` (`step-executor.ts:1263-1265`). The rest of the attempt is then delivered only through checkpoints and the tree poll.
- **Cause:** fencing correctness was designed per event: each part re-proves the claim against PostgreSQL. Per token that means about 2 DB transactions plus about 7 Valkey round trips, serialized with the provider stream. At full concurrency and roughly 30–60 deltas/s per run, that is hundreds of DB transactions per second from streaming alone. They contend with heartbeats and checkpoints for 5 connections, so under load the live stream degrades to snapshot mode instead of shedding work.
- **Why the evidence does not cover it:** the F4.2 S2 burst measured SSE admission, first-frame latency and auth-pool wait (`F4.2-acceptance.md` Gate 6.5). It did not measure per-delta publish latency, app-pool wait in the AI worker, or how often runs fall back to snapshot mode under real token rates.
- **Suggested fix (smallest safe):**
  - Coalesce deltas in the executor: flush every N ms (for example 50 ms) or every M bytes, so one publish carries many tokens.
  - Within one publish, reuse the first `#activeProof` unless the registry reconcile path ran. The second proof at `:553` exists only for that path.
  - Size the AI-worker pool above its job concurrency (a per-runtime `DATABASE_POOL_MAX`).
  - Record a K3 counter of snapshot-mode fallbacks per run.
- **Test to add:** yes.
  - A unit test with a fake model that emits 200 one-character deltas: assert at most ⌈duration/flush⌉ publishes, and at most one `authorizeActive` per publish when no reconcile happens.
  - An integration test: with a 150 ms injected DB delay per transaction, a 200-delta answer still streams live (no `streamSnapshotRequired`).

### B-03: A-02 partly holds: exhausted serialization retries return 500, and `ECONNREFUSED` is labelled an auth outage

- **Severity:** Minor. **Theme:** 2 (error paths).
- **Evidence:**

### B-22: The live answer's Markdown elements are remounted on every streamed delta

- **Severity:** Minor. **Theme:** 4.
- **Evidence:**
  - `frontend/src/components/chat/markdown-text.tsx:77-143` builds the `components` map (`img`, `h1`–`h3`, `p`, `ul`, `ol`, `strong`, `li`, `blockquote`, `a`, …) inside `MarkdownBody` on every render, as new inline functions.
  - `MarkdownText` receives the part's text as a prop (`:48-63`), so it re-renders on each streamed delta.
  - The library keeps `components` stable only if each entry is identical (`useStableProps`, `@assistant-ui/react-markdown@0.14.25` `dist/primitives/MarkdownText.js:72-78,102-109`). New functions defeat that, so `ReactMarkdown` gets new element types on every render.
  - `assistant-ui/elements/thread.aui.tsx:480` also passes an inline `components={{ Text: MarkdownText, Reasoning: () => null }}`.
  - **Reproduced** with the pinned React 19.3.1 and react-markdown 10.1.0 (a throwaway script, no repo files). With an inline map, the first `<p>` DOM node is replaced after a text append. With a hoisted map, it is kept.
  - So every paragraph, list item and link of the live answer is unmounted and recreated on each delta. On long answers this is wasted work, and the user loses a text selection or link focus while the answer streams. The F4.2 G4 stress run recorded long tasks of up to 227 ms at 4× CPU (`F4.2-acceptance.md`, Task 3C), but it did not isolate this cause.
- **Suggested fix:**
  - Hoist two constant maps (normal and dimmed) to module scope, or `useMemo` the map on `dimmed`.
  - Hoist the `Parts` components object in `thread.aui.tsx`.
- **Test to add:** yes. In `frontend/test/chat-markdown.spec.tsx`, render a live answer with a paragraph and a link, append text, and assert that the first `<p>` and the `<a>` are the same DOM nodes as before.

### B-23: The shared identity error contract is out of sync with the codes the server emits

- **Severity:** Minor. **Theme:** 5 (contracts in `shared/`) and 6.
- **Evidence:**
  - **Declared but never emitted:** `IdentityErrorCodeSchema` (`shared/src/auth.ts:93-108`) lists 14 codes. Two of them, `AUTH_DISABLED` (`:98`) and `INVITATION_UNAVAILABLE` (`:106`), are never thrown in `backend/src`; disabled users get `AUTH_REQUIRED` 401 (`identity-access/identity-policy.ts:21`).
  - **Emitted but not declared**, on identity and organization routes:
    - `SafeErrorFilter` emits `CONFLICT` (`error.filter.ts:168`), `REQUEST_REJECTED` (`:178`), `NOT_FOUND` (`:175`), `INVALID_JSON` (`:150`) and `INTERNAL_ERROR` (`:119`);
    - the Better Auth bridge emits `EMAIL_NOT_VERIFIED` (`identity-access/auth-output.ts:177`).
  - **What the client does with them:**
    - `frontend/src/lib/identity-client.ts:105-111` parses error bodies with the strict `IdentityErrorResponseSchema`. Any of the codes above fails that parse and becomes `AUTH_UNAVAILABLE` with the original status (or `AUTH_REQUIRED` for a 401).
    - So the 409 that A-02 introduced for lost state races reaches the UI as `AUTH_UNAVAILABLE`/409, and `identityMessage` (`components/organizations/page-state.tsx:15-25`) shows the generic "Unable to complete this action…" text.
    - The login form matches `EMAIL_NOT_VERIFIED` by raw string (`components/auth/login-form.tsx:16-24`), outside the contract.
- **Cause:** the codes were added in different slices (F1 contract, F1 bridge, F4.2 filter) with no test tying emitted codes to the shared enum.
- **Suggested fix:**
  - Make the enum the source of truth. Add `EMAIL_NOT_VERIFIED`, or map it to the existing `AUTH_EMAIL_VERIFICATION_REQUIRED`.
  - Add a state-conflict code, for example `ORG_STATE_CHANGED` as audit 1 proposed, and use it for identity-route 409s.
  - Remove `AUTH_DISABLED`/`INVITATION_UNAVAILABLE`, or implement them.
- **Test to add:** yes.
  - A contract unit test: run the filter and the bridge on each error class they map, and assert that the body parses with the schema the client uses for that route family.
  - A frontend test: a 409 race shows a "this changed, refresh" message.
