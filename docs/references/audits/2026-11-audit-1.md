## What is solid

- **Tenant isolation in `app.*`.** All 15 `app` tables have `ENABLE` and `FORCE ROW LEVEL SECURITY`. Policies use the fail-closed `NULLIF(current_setting('app.org_id', true), '')::uuid` form (LEX-ARC-001:196). Chat tables add owner and live-chat checks. No role has `BYPASSRLS`. `USING (true)` policies exist only `TO lexon_migrator`, the owner of the trigger and definer functions. `withTenant` sets context with `set_config(..., true)` inside `BEGIN`, so the setting is transaction-local, and a failed rollback destroys the connection (`backend/src/infrastructure/db/tenant-database.ts:155-161,197-226`). The `auth.*` schema has no tenanted RLS by design (LEX-ARC-001:190); it is protected by role separation and column grants (`backend/drizzle/0004_personal.sql:106-110`).
- **SECURITY DEFINER hygiene.** Every function pins `search_path` and revokes `PUBLIC`. Every `ops.ai_*` definer function executable by `lexon_app` compares its arguments to `app.org_id`/`app.user_id` and fails closed (for example `0026_chat_tree.sql:235-255`, `0033_chat_cleanup.sql:101-369`, `0028_chat_queued_privacy.sql:1-23`).
- **Auth surface.**
  - Better Auth is reachable only through an allowlist (`identity-access/auth-endpoints.ts:9-131`), with path normalisation, a 32 KB body cap, same-origin callback URLs, and Origin / `sec-fetch-site` checks.
  - `TenantGuard` runs the Origin check on every non-GET Nest route before identity resolution (`tenant.guard.ts:76`, `identity-runtime.ts:159-169`).
  - Credential-channel separation (cookie vs bearer) is enforced at the request and in the session row.
  - Platform actions require admin, MFA, and re-authentication within 300 s (`organization-auth.port.ts:48-67`).
  - The rate limiter fails closed (503) when Valkey is down.
  - Admin-setup tokens are stored as digests and cannot be replayed after completion.
- **Privacy controls.**
  - Pino output is rebuilt from an allowlist: no URL/query, `err` reduced to `{type:'Error'}`, messages forced to a constant (`infrastructure/telemetry/logging.ts:20-153`).
  - OTel export is allowlisted, and AI SDK `recordInputs`/`recordOutputs` are `false` (`ai-telemetry.ts:12-22,193-233`; `model-gateway.ts:185-195`).
  - Audit metadata is key-allowlisted in both Zod and SQL triggers. Job and outbox envelopes carry ids only.
  - Chat deletion purges rows, cascades, Valkey streams and permits, and snapshots usage first. `usage_events` has no FK, and `DELETE` is revoked (`0024_usage_event_privileges.sql`).
- **Queue correctness.**
  - The outbox append runs in the caller's transaction. Claims use `FOR UPDATE SKIP LOCKED` with a lease. The BullMQ `jobId` is the outbox id. `markSent` is lease- and token-guarded.
  - Step claims are fenced in SQL against database time (`ai-step.repository.ts:557-975`), and stream publication is fenced in Lua.
- **Supply chain.**
  - Every dependency is pinned exactly (`saveExact: true`, no ranges).
  - The lockfile contains exactly one TypeScript (6.0.3) and one Zod (4.6.7).
  - GitHub Actions are pinned by SHA, and container images by tag and digest (`config/container-images.env`).
  - Compose publishes ports on `127.0.0.1` only, and the runtime services are `read_only` with `cap_drop: ALL`.

## Findings

### A-01 — A duplicate organization slug returns 500 on create, rename and platform provisioning

- **Severity:** Important. **Theme:** 3 (error paths returning 500 instead of 4xx). This confirms the known example.
- **Where:**
  - `backend/src/modules/organizations/organization.service.ts:107-110` (create)
  - `organization.service.ts:160-170` (rename / slug change)
  - `backend/src/infrastructure/db/auth/provisioning-plugin.ts:42-66` (platform provisioning)
  - `backend/src/infrastructure/db/auth/auth-transaction.ts:116-122`
  - `backend/src/modules/platform/error.filter.ts:26-30`
- **What is wrong:** there are three slug-writing paths, and none maps a conflict to a 4xx.
  1. `POST /api/organizations` calls Better Auth's `createOrganization` through `tx.call`. Better Auth checks the slug and **throws** `APIError("BAD_REQUEST", ORGANIZATION_ALREADY_EXISTS)` (`node_modules/better-auth/dist/plugins/organization/routes/crud-org.mjs:62`). `tx.call` converts only a _returned_ `Response` with status ≥ 400. A thrown `APIError` propagates unchanged through `OrganizationAuthPort.transaction` (`organization-auth.port.ts:98-107`, rethrown because it carries no 40001/40P01/`lexon_team_owner` marker). `SafeErrorFilter` has no `APIError` branch, so the response is **500 `INTERNAL_ERROR`**.
  2. `PATCH /api/organizations/:id/settings` with a taken slug: Better Auth throws `APIError("BAD_REQUEST", ORGANIZATION_SLUG_ALREADY_TAKEN)` (`crud-org.mjs:214-215`), which also becomes **500**.
  3. `POST /api/platform/provisioning`: `lexonProvisionTeam` calls `adapter.create({model:'organization', data:{slug,…}})` **with no existence check**. The `organization_slug_unique` constraint (`backend/drizzle/0003_auth.sql:54`) raises 23505, which also becomes **500**.
  - Even after a pre-check is added, two concurrent creates can both pass it, and the second one hits 23505.
- **Evidence:**
  ```ts
  // auth-transaction.ts:119-121
  const result = await invoke(input);
  if (result instanceof Response && result.status >= 400)
    throw new Error('Auth command failed');
  ```
  ```ts
  // error.filter.ts:26-30 — default branch reached by APIError and pg errors
  let status = 500;
  let detail = { code: 'INTERNAL_ERROR', message: 'Internal server error' };
  ```
  `IdentityErrorCodeSchema` (`shared/src/auth.ts:69-82`) has no slug-conflict code, so the frontend cannot show "slug taken". No test covers the case (see A-17): every test uses a random slug.
- **Violates:** F1 brief 10a and 15 (team creation and slug settings are user-facing flows), and AGENTS.md TDD. The architecture's error-shape contract expects expected client errors to be typed.
- **Suggested fix (smallest safe):**
  - Add `ORG_SLUG_TAKEN` (409) to `IdentityErrorCodeSchema`.
  - In `OrganizationAuthPort.transaction`'s catch, map two cases to `IdentityError('ORG_SLUG_TAKEN', 409)`:
    - `APIError` with body code `ORGANIZATION_ALREADY_EXISTS` or `ORGANIZATION_SLUG_ALREADY_TAKEN`;
    - `databaseFailure(...).constraint === 'organization_slug_unique'` (extend `databaseFailure` to return that constraint).
  - Show the code inline on the create-team and settings forms.
- **Test to add:** yes. Integration tests for create, rename and provisioning with an existing slug, expecting 409 `ORG_SLUG_TAKEN`. Add one concurrent-create test that expects exactly one 201 and one 409.

### A-02 — `SafeErrorFilter` turns Better Auth errors, pg errors and most `HttpException`s into 500

- **Severity:** Important. **Theme:** 3 (timeouts, 500 vs 4xx) and 4 (inconsistent error shapes).
- **Where:**
  - `backend/src/modules/platform/error.filter.ts:31-64`
  - `backend/src/modules/identity-access/organization-auth.port.ts:98-109`
  - `backend/src/infrastructure/db/auth/auth-integration.ts:11-16`
  - `backend/src/modules/identity-access/tenant.guard.ts:100-102`
- **What is wrong:** the filter recognises `IdentityError`, `ChatApiError`, `ZodError`, `ValidationFailure`, body-parse errors, and `HttpException` with status 400 or 404. Everything else is 500. Inside organization, membership, invitation and provisioning services, that includes:
  - Better Auth `APIError`s thrown by the stock plugin and by Lexon's own plugins. Lexon's plugins throw `APIError('CONFLICT', …)` on state races, for example `invitation-plugin.ts:142,168,231,271,284,334,359`, `provisioning-plugin.ts:120`, `session-plugin.ts:60`, `admin-setup-plugin.ts:83`. A lost race therefore surfaces as 500, not 409. (The services pre-check state, so this occurs on concurrent requests, not on the happy path.)
  - The **auth-pool acquire timeout**. The pool has `max: 5` and `connectionTimeoutMillis: 10000` (`auth-integration.ts:11-16`). pg throws a plain `Error("timeout exceeded when trying to connect")`.
    - The guard maps any non-`IdentityError` to 503 `AUTH_UNAVAILABLE` (`tenant.guard.ts:100-102`), and `IdentitySessionService.transaction` does the same (`identity-session.service.ts:104-120`).
    - `OrganizationAuthPort.transaction` rethrows it raw (`organization-auth.port.ts:102-106`), so the same outage is **503 at the guard but 500 in the service**.
    - Line 109 (`throw new IdentityError('AUTH_UNAVAILABLE', 503)`) is unreachable: `attempt === 2` rethrows first.
  - Serialization failures (40001/40P01) that remain after the third attempt are also rethrown raw, giving 500.
  - Any 401/403/409/413/429/503 `HttpException` becomes 500 (none are thrown today; the filter would hide them).
- **Evidence:**
  ```ts
  // organization-auth.port.ts:98-109
  } catch (error) {
    const failure = databaseFailure(error);
    if (failure.constraint === 'lexon_team_owner')
      throw new IdentityError('ORG_LAST_OWNER', 409);
    if (attempt === 2 || (failure.code !== '40001' && failure.code !== '40P01'))
      throw error;                      // raw pg / APIError → 500
  }
  }
  throw new IdentityError('AUTH_UNAVAILABLE', 503); // unreachable
  ```
- **Violates:** the F1 design treats `AUTH_UNAVAILABLE` 503 as the dependency-failure outcome (`docs/superpowers/plans/2026-10-31-f1-identity-organizations.md:309`: "throws safe 429 or 503 outcomes").
- **Suggested fix:** in `OrganizationAuthPort.transaction`, after the last attempt:
  - map retryable or pool-acquire failures to `IdentityError('AUTH_UNAVAILABLE', 503)`;
  - map `APIError` by `statusCode`: 409 becomes `IdentityError('ORG_FORBIDDEN' | new 'ORG_STATE_CHANGED', 409)`, and other 4xx become 400/403;
  - keep 500 only for unknown errors.
  - In `SafeErrorFilter`, pass through `HttpException` status codes with a fixed safe message per status, rather than defaulting to 500.
- **Test to add:** yes. Unit-test `OrganizationAuthPort` with an injected integration that throws (a) a pg acquire-timeout error, (b) `APIError('CONFLICT')`, and (c) 40001 three times. Assert 503, 409 and 503 respectively.

### A-03 — `AUTH_TRUSTED_PROXIES` is never set, so all clients behind Caddy share one IP rate-limit bucket

- **Severity:** Important. **Theme:** 1 (rate limits) and 7 (production configuration). In the shipped Compose topology this is an exploitable denial of service against authentication. It must be fixed before F20 ships production Compose.
- **Where:**
  - `backend/src/modules/identity-access/client-address.ts:15-37`
  - `backend/src/config/auth-rate-config.ts:22-31,64-68`
  - `docker-compose.yml:183-217` (api service)
  - `infra/Caddyfile:5-14`
  - `.env.example`
- **What is wrong:**
  - `resolveClientAddress` honours `X-Forwarded-For` only when the socket peer is in `AUTH_TRUSTED_PROXIES`. The default is an empty list.
  - Browser traffic reaches the API through Caddy (`reverse_proxy api:3001`), so the peer is always the Caddy container.
  - `AUTH_TRUSTED_PROXIES` appears nowhere in `docker-compose.yml`, `.env.example`, or the docs outside the F1 plan.
  - Every per-IP limit is therefore one global bucket:
    - `signin` 30 per 60 s;
    - `signup` and `reset` 10 per 600 s;
    - `totp` 30 per 300 s.
  - An anonymous client sending 10 sign-up requests in 10 minutes blocks sign-up for everyone, and 30 bad sign-ins per minute block everyone's sign-in. Per-IP limiting of a real attacker is ineffective.
- **Evidence:**
  ```ts
  // client-address.ts:29-30
  let current = normalize(peer);
  if (!allowed(current)) return current; // peer = Caddy container IP
  ```
  `grep -rn AUTH_TRUSTED_PROXIES docker-compose.yml .env.example` → 0 matches.
- **Violates:** F1 brief, "Rate limits trigger on repeated failures" (the limits are meant per client); F1 plan Task 6, "AUTH_TRUSTED_PROXIES for validated explicit proxy addresses".
- **Suggested fix:**
  - Give Caddy a fixed address on the `edge` network, or use the `edge` subnet CIDR.
  - Set `AUTH_TRUSTED_PROXIES` to it in the api service, and add the variable to `.env.example` with a comment.
  - Optionally fail boot when `AUTH_LOCAL_DEVELOPMENT=false` and the list is empty.
- **Test to add:** yes. Add a Compose-level script spec (in the style of `scripts/test/identity-compose.spec.mjs`) asserting the api service sets `AUTH_TRUSTED_PROXIES` to Caddy's network. The unit tests for `resolveClientAddress` already exist.

### A-04 — SSE re-authorization costs one auth-pool transaction per second per stream, and S2 evidence did not exercise it

- **Severity:** Important (capacity/reliability risk; not measured). **Theme:** 3 (SSE hub limits and recovery; auth pool).
- **Where:**
  - `backend/src/modules/chat/run-events.service.ts:294-307` (`/api/chats/events`)
  - `run-events.service.ts:376-415,419-437` (run streams)
  - `backend/src/modules/identity-access/identity-session.service.ts:74-120`
  - `backend/src/infrastructure/db/auth/auth-integration.ts:11-16`
  - `backend/test/e2e/chat-sse-load.spec.ts:136-149,195,881`
  - `backend/test/e2e/compose.chat-load.yml`
- **What is wrong:**
  - Every open `/api/chats/events` connection runs `registry.renew` and then `revalidation.assert(identity, orgId)` **every 1000 ms, uncached**. That function is a full auth transaction (`assertRunSseSelection`: session, user and selection facts) on the `lexon_auth` pool, which has `max: 5` per API process. The frontend opens this stream for every signed-in workspace tab (`frontend/src/components/shell/workspace-provider.tsx:224-240`).
  - Run streams use the same check, cached for 1 s per `(user, run, channel, session)`.
  - Identity polling adds one guarded request per tab every 5 s.
  - The load is therefore at least one auth transaction per second per open tab. When the pool saturates:
    1. the 10 s acquire wait elapses;
    2. `revalidation.assert` throws, and the stream is closed as `revoked`, which ends the response;
    3. the client treats the EOF as an interruption and reconnects through `TenantGuard`, which needs the same pool (it gets 503, which is retryable).
  - This amplifies load instead of shedding it.
- **Why the S2 evidence does not cover it:**
  - `F4-sse-load.json` shows 2 owners × 250 subscribers, and every subscriber reuses its owner's cookie (`chat-sse-load.spec.ts:136-149`). The 1 s cache therefore collapsed 250 checks into 1 per second per owner.
  - Only `/api/runs/:id/events` was loaded (`:195`); `/api/chats/events` was not.
  - The API ran with 1536 MiB and 1 CPU (`compose.chat-load.yml`), while the Compose runtime anchor gives it 384 MiB and 0.5 CPU (`docker-compose.yml:13-14`).
  - The run was `sourceDirty: true`, and Linux final-head verification is recorded as pending (`F4-acceptance.md:1676,1812`).
- **Evidence:**
  ```ts
  // run-events.service.ts:294-303 (chat invalidation stream)
  renewal = setInterval(() => {
    …
      const current = await this.registry.renew(lease!);
      if (!current) return close('evicted');
      lease = current;
      await this.revalidation.assert(identity, orgId); // auth tx, every second
    })().catch(() => close('revoked'))
  }, 1000);
  ```
- **Violates:** F4 brief S2, "≥ 500 concurrent SSE connections" (the evidence is not representative of distinct sessions or the invalidation stream); LEX-ARC-001 §5.3 resource budget.
- **Suggested fix (smallest safe):**
  - Apply the run stream's 1 s `(user, session, org)` cache to the invalidation stream too, so one session's tabs share one check.
  - Raise the revalidation interval to about 5 s, matching identity polling. Revocation is also pushed by the deletion and cancel signals.
  - On an `AUTH_UNAVAILABLE` revalidation failure, keep the stream open and retry, rather than closing it as `revoked`. Close only on a definite 401/403.
  - Re-run S2 with distinct sessions, both stream types, and the Compose resource limits.
- **Test to add:** yes. A unit test proving N invalidation streams for one session cause at most one revalidation per interval, and that `AUTH_UNAVAILABLE` does not close the stream. Also a load-evidence run with one session per subscriber.

### A-05 — A Valkey failure during SSE admission returns 404, which the client treats as non-retryable

- **Severity:** Minor. **Theme:** 3.
- **Where:** `backend/src/modules/chat/run-events.service.ts:335-347`; `frontend/src/lib/chat-transport.ts:666-668`.
- **What is wrong:**
  - A thrown `registry.admit` (Valkey down or timed out) is converted to `NotFoundException`.
  - The transport retries only on status ≥ 500 (or EOF).
  - A short Valkey outage therefore ends a live stream with a 404, without the bounded retry the transport implements.
  - 404 is correct for "not your run". It is not correct for "dependency unavailable".
- **Evidence:**
  ```ts
  } catch {
    throw new NotFoundException();   // registry.admit failure
  }
  ```
  ```ts
  return error.code !== 'AI_ACCESS_REVOKED' && error.status >= 500;
  ```
- **Suggested fix:** throw `ChatApiError('AI_PROVIDER_UNAVAILABLE' | a stream-unavailable code, 503)` from the admission catch. Keep 404 for the ownership check.
- **Test to add:** yes. An integration test with a failing registry, expecting 503 and a retry by the transport.

### A-06 — Outbox poison rows retry forever, and the oldest-entry age signal is missing

- **Severity:** Minor. **Theme:** 3 (outbox idempotency and operations).
- **Where:** `backend/src/modules/platform/outbox-dispatcher.ts:55-72`; `backend/src/infrastructure/db/outbox.repository.ts:59-104`.
- **What is wrong:**
  - A row whose payload fails `parseJobEnvelope` gets `last_error_code='invalid_job'` and is rescheduled with capped exponential backoff (cap 30 s). There is no attempt limit, dead-letter state, or alert, so a poison row is re-claimed about every 30 s indefinitely.
  - Enqueue failures behave the same way. That is correct for outages, but there is no visibility.
  - LEX-ARC-001:691 lists "age of the oldest outbox entry" as an operational signal. `grep -rni oldest backend/src` finds only stream-hub code.
- **Evidence:** in `outbox-dispatcher.ts:64-72`, `if (!claim.job) { await this.repository.reschedule(claim.id, claim.claimToken, nextAttempt(), 'invalid_job'); continue; }`.
- **Violates:** LEX-ARC-001:691 (metric).
- **Suggested fix:**
  - Stop rescheduling `invalid_job` rows after N attempts, for example by setting `next_attempt_at = 'infinity'` and keeping `last_error_code`.
  - Expose `min(created_at) WHERE sent_at IS NULL` in the dispatcher health snapshot.
- **Test to add:** yes. A dispatcher integration test: a malformed row stops being claimed after N attempts, and the health snapshot reports its age.

### A-07 — Chat client polls the full tree every second during active runs

- **Severity:** Minor. **Theme:** 6. This **confirms** the F4 review finding.
- **Where:**
  - `frontend/src/components/chat/chat-runtime.tsx:164-234`
  - `frontend/src/components/chat/chat-view.tsx:86-92`
- **What is wrong:**
  - While `serverActiveRunId` is set, a chained 1000 ms `setTimeout` calls `client.get(chatId)`. That is the whole message tree, every branch, with no `AbortSignal`.
  - This runs in parallel with the SSE stream, which already carries the live content.
  - There is no `document.hidden` pause and no backoff.
  - Failures are swallowed (`catch { /* Keep controls locked … */ }`, `:217-219`), so a persistent failure leaves controls locked with no message.
  - Server cost is one RLS-checked tree query per second per active chat tab, in addition to the stream.
- **Evidence:** `timer = window.setTimeout(() => void refresh(), 1_000);` at `:220,222`. `grep visibilitychange frontend/src` returns 0 matches.
- **Violates:** none directly. LEX-ARC-001 §4.1 makes SSE the live channel; polling is a safety net.
- **Suggested fix (smallest safe):** keep the poll as the terminal-state safety net, but:
  - use 1 s only while the transport reports `reconnecting`, or before the first frame arrives, and 5 s otherwise;
  - skip ticks while `document.hidden`;
  - pass an `AbortSignal` to `client.get` and abort it in the effect cleanup;
  - after about 5 consecutive failures, show the existing reconnecting/error state rather than staying silent.
- **Test to add:** yes. Fake-timer tests in `chat-runtime.spec.tsx` for the cadence switch, the hidden-tab pause, abort on unmount, and surfacing after repeated failures.

### A-12 — Intermittent: `ai-execution.spec.ts` "renews a short-lived claim while the context collector is delayed"

- **Severity:** Minor. **Theme:** 5 (known intermittent: **explained**).
- **Where:** `backend/test/integration/ai-execution.spec.ts:5332-5365`; `backend/src/modules/chat/step-executor.ts:2205-2230`.
- **Cause:**
  - The test uses `leaseMs: 90` and a collector that sleeps 260 ms.
  - The heartbeat interval is `floor(90/3) = 30` ms, but the next renewal is scheduled only **after** the previous `coordinator.renew` resolves. Each renewal is a real Postgres transaction with row locks.
  - The real gap between renewals is therefore 30 ms plus the round trip. If one renew takes about 60 ms or more on a loaded CI database (Testcontainers, `maxWorkers: 2`), `lease_until` lapses, the next renew returns `false`, and the executor aborts with `AI step claim lost`. The `resolves.toEqual({kind:'done'})` assertion then fails.

  - Production uses a 30 s lease and a 5 s interval, so this is a test-tuning problem, not a production bug.
- **Evidence:**
  ```ts
  timer = setTimeout(() => {
    renewal = (async () => {
      if (!(await coordinator.renew(claim))) controller.abort(new Error('AI step claim lost'));
      …
      if (!controller.signal.aborted) schedule();   // next tick only after round trip
  ```
- **Suggested fix:** use `leaseMs: 600` with a 1800 ms collector delay. That keeps the "≥ 2 renewals while delayed" property with about 20× more margin. Alternatively, inject a fake coordinator clock.
- **Test to add:** no (adjust the existing test).

### A-13 — Intermittent: `ai-streams.spec.ts` "a stale claim fence cannot publish after a newer claim"

- **Severity:** Minor. **Theme:** 5 (known intermittent: **explained**).
