## Residuals and introduced breakage

### R1 — Important: expired public cancellation commits a step without advancing its terminal lineage

**Sources:** `backend/src/modules/chat/cancel.service.ts:81` and `:102`; `backend/src/infrastructure/db/ai-run.repository.ts:322`; `backend/src/infrastructure/queue/run-streams.ts:815`. Compare the already-correct coordinator expired-cancellation transition at `backend/src/modules/chat/step-coordinator.ts:535`.

Take a run at current sequence 1 with an expired claimed step and an active stream. The new public-cancel branch successfully calls `commitExpiredCancellation`, changing that step to committed and settling its attempt. It then transitions the run to cancelled without passing `nextSequence`; `AiRunRepository.transition` preserves sequence 1. `terminalStreamReference` now selects this real committed step and returns a **non-neutral** reference. `RunStreams.#terminalProof` requires a non-neutral terminal run to have `nextSequence >= reference.sequence + 1`, so it refuses this reference: 1 is not >= 2.

This is not merely missing test coverage. The durable ledger repair succeeds, but the terminal status/finish is never emitted on this path. Registry reconciliation obtains the same terminal lineage and cannot finalize it either. An existing active stream can therefore remain in the active pool without its terminal TTL; later publications encountering it during reconciliation can be refused, consuming bounded stream capacity after SQL admission was released. Terminal job redelivery is a no-op and does not advance the sequence.

**Required correction:** Advance the run sequence atomically when the public path commits the expired current step, matching the coordinator path. Keep the different pending/no-committed-step cancellation case's neutral lineage valid; do not relax terminal proof or fabricate a neutral reference for a committed step. Preserve unknown full reserve, known observations, partial output once, audit, and admission release.

**Missing regression:** Extend the public expired-cancel test with real RunStreams, an existing open stream, sequence assertion, terminal status/finish, removal from active registry/TTL, repeated cancel, and reconciliation/redelivery. Its present assertions establish ledger closure only.

### R2 — Important: the new lifecycle producer silently drops every event for a valid larger approval batch

**Sources:** `backend/src/modules/chat/step-executor.ts:1350`, `:1360`, `:1388`; `backend/src/infrastructure/queue/run-streams.ts:314`; accepted proposal persistence at `backend/src/modules/chat/step-coordinator.ts:217` and `backend/src/infrastructure/db/ai-operation.repository.ts:92`.

A valid generation may propose 16 approval-required transactional operations. Neither proposal validation nor the durable operation loop limits that valid case below 16. After committing awaiting approval, `#publishCommittedLifecycle` constructs one status plus one operation-status and one approval-required event per operation: **1 + 2×16 = 33**. `publishCommitted` returns `stale` immediately for more than 32 events, before any append. The caller ignores the result. Thus all operations are durably staged and execution ends, but none of their required notifications is published even with a healthy database/Valkey and ample time. The existing notification tests cover a single operation only.

This is a deterministic producer/writer contract mismatch, not the accepted possibility of transient notification loss. It leaves original I6 incomplete and is introduced by the new producer API. The same mismatch occurs at other combinations of accepted operation statuses that exceed the event bound.

**Required correction:** Make accepted operation cardinality and notification cardinality coherent. Bound/reject unsupported proposals before committing a paused state, or publish the supported set through bounded processing that retains the original deadline, ordering, finite schemas, and stale-lineage checks. Do not silently truncate approval notices, raise the 250 ms deadline, or add an unbounded/reliable event log.

**Missing regression:** Stage a supported batch at the boundary and immediately above it through the executor, inspect actual Valkey notifications, and assert either safe pre-staging refusal or the required events for every durably awaiting operation. Include the one-status/two-per-approval arithmetic explicitly.

**Additional I6 evidence qualification:** `backend/test/integration/ai-execution.spec.ts:1922` awaits the executor while its approval-required EVAL is held. The executor can return only after that publication's 250 ms timeout; the approval decision and old-EVAL release occur afterward. The late EVAL is therefore already expired when it reaches the Lua script. Absence of that event does not independently prove that the v3 guard, rather than the expiry check, rejected v2. The source has the intended version comparison, and the later fresh `publishCommitted` call proves DB refusal, but the report's specific claim of an observed cross-instance v3 Lua fence is overstated. A distinct controlled unexpired stale-version EVAL should observe the guard rejection to establish that particular proof, without extending production timeout.

### R3 — Minor: stale tool continuation commits still emit succeeded/continued telemetry

**Source:** `backend/src/modules/chat/step-executor.ts:553` through `:565`.

In the transactional-tool continuation branch, `coordinator.commit` can return `stale` when ownership expires or another owner wins before the transaction's claim check. The conditional block runs only for a committed result, but execution then always calls `setRunSpanStatus('continued')` and `setStepSpanStatus('succeeded')`. No successful tool-step commit is required for those labels. Similar early lifecycle status branches should be checked when completing M1; the model-generation branch's new committed-result read does not cover them.

Durable fencing/effect rollback remains intact, so this is observability correctness rather than an established unauthorized effect. It nevertheless leaves the requested stale/not-committed status correction incomplete.

**Required correction:** Derive statuses from the commit outcome on the tool continuation path too, and preserve meaningful failed/continued semantics for actual tool timeout results. Add a deterministic stale-tool-commit span assertion; the current added M1 tests exercise generation refusal/overrun/iteration, not this branch.

### R4 — Minor: the timeout safety test disconnects instead of proving settled no-late-write behavior

**Sources:** `backend/test/integration/ai-streams.spec.ts:2187` through `:2193`; `backend/src/infrastructure/queue/run-streams.ts:402` (`close`); terminal-member construction in `backend/src/infrastructure/queue/run-stream-scripts.ts` FINISH.

After the public promise times out, the test releases its authorization barrier and calls `staleWriter.close()`. That method only calls `disconnect()`; it does not await the running queue task. Awaiting `pendingPublish` again observes the already-resolved timeout wrapper, not the underlying task. Consequently the following absence assertions can run before the released task reaches its remaining path, and disconnecting can itself prevent the write the test intends to exclude. This is not the requested proof with an operating writer after delayed authorization settles.

The new `zscore(terminalKey, original.id)` assertion is also ineffective: FINISH stores members as `runId|generation`, not plain `runId`. It would return null even if the target had acquired terminal membership.

**Required correction:** Keep the connection usable, capture/await the underlying released task's completion through deterministic test synchronization, then assert no stream/guard/active or terminal recreation. Check terminal membership using the actual stored member/index or a run-prefix match. Preserve the separate deterministic PREPARE epoch-mismatch case and the existing deadline; do not restore the original flaky combined timing assertion or accept a result union. This residual does not invalidate the separate R50 delayed-EVAL tests, which do await their held commands.
