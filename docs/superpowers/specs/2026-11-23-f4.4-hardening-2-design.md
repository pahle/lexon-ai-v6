## 1. Standing rules (every later phase)

- **Subagents:** explore subagents for research and reading; general subagents only for code changes and task reviews; no custom subagent files.
- **Session stats:** run `/session-stats` before task 1 starts and again after task 1 is reviewed; attach both outputs (cost by model) to the task 1 report.
- **TDD with RED evidence for every task:** the failing command and its output before the change, and the passing run after.
- **Reviews:** a spec review and a quality review per task; the report lists each finding and how it was handled.
- **PR:** a draft PR from the first task. Every report states the CI result of its head (`gh pr checks <n>` once, no polling; verify exit codes).
- **Assertions:** never weaken a functional, accessibility or security assertion; log every changed assertion old → new.
- **Docker:** only touch containers and volumes named `lexon-e2e-*`, by explicit name filter. Never prune. Never touch the unnamed volume `a4699d7d…` or any `lexon-dev_*` volume. If disk space or leftover stacks block a gate, stop and ask the owner.
- **No model names** in commits, PRs or repo files.
- Clean room (AGENTS.md): work only from `docs/` and the code; never read the `brief-generator` branch; never read, print or commit `.env` files or keys.

## 2. Caps and stop points

- No visual rounds. No golden, screen or prototype change.
- At most **2 Linux runs** for the load check (item 19) and at most **2 Linux runs** for the 20-pass flake counters (items 6, 7). Extra runs need the owner.
- **Stop and ask the owner** if:
  - any golden changes (do not re-approve it);
  - a vulnerable chain has no safe version, or an override guard (§4.3) fails and a small fix does not solve it — ask for that chain only; a reasoned allowlist entry needs the owner's approval; never extend an expiry;

  - official docs contradict `docs/specs/`;

### Item 5 — B-07 catalog, `ops` inventory, default privileges (still holds)

Today `0000_foundation_roles.sql:17-18` grants, as a **per-schema** default for `lexon_migrator`:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE lexon_migrator IN SCHEMA app, ops
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO lexon_app;
```

PostgreSQL 17 docs say a per-schema REVOKE only reverses a previous per-schema GRANT. Because this grant is per-schema and there is no global grant, a per-schema revoke removes it cleanly.

**Migration** `backend/drizzle/0041_ops_default_privileges.sql` (next free number; implementer confirms), applied as `lexon_migrator`:

```sql
ALTER DEFAULT PRIVILEGES FOR ROLE lexon_migrator IN SCHEMA ops
  REVOKE SELECT, INSERT, UPDATE, DELETE ON TABLES FROM lexon_app;
ALTER DEFAULT PRIVILEGES FOR ROLE lexon_migrator IN SCHEMA ops
  REVOKE USAGE, SELECT ON SEQUENCES FROM lexon_app;
```

- It touches no existing `ops` table's or sequence's grants (`ALTER DEFAULT PRIVILEGES` affects only future objects). Owner decision 1 (2026-11-23): the `ops` sequence default is narrowed too; `app` defaults (tables and sequences) are unchanged. A future `ops` table that needs a sequence grants it explicitly in its own migration.
- The drizzle journal entry is added the same way as for earlier migrations.

**Tests** (integration, Testcontainers):

1. **Default-ACL pin (RED on main):** read `pg_default_acl` joined to `pg_namespace` for `defaclrole = lexon_migrator`, across **every** `defaclobjtype` (owner amendment 5), and assert `lexon_app`'s entries: `app` exactly as today (tables `arwd`, sequences `rU`), and nothing of any type in `ops`. On main, `ops` shows tables `arwd` and sequences `rU`, so the test is RED.
2. **New table proof (RED on main):** in a transaction as `lexon_migrator`, `CREATE TABLE ops.f44_probe(id int)`, then `has_table_privilege('lexon_app', 'ops.f44_probe', p)` is false for SELECT, INSERT, UPDATE and DELETE; likewise `CREATE SEQUENCE ops.f44_probe_seq` gives `has_sequence_privilege('lexon_app', …)` false for USAGE and SELECT; then roll back.
3. **`ops` inventory:** for every `relkind IN ('r','p')` table in `ops`, list its `text`/`jsonb` columns and `lexon_app`'s privileges, and compare with an explicit allowlist (`outbox`, `processed_jobs`, `audit_events`, `ai_engine_capacity`, `ai_run_slots`). A new table, a new K1-capable column, or a new `UPDATE`/`DELETE` grant fails. Existing grants are pinned before and after the migration, unchanged.

### Item 15 — B-04 cancellable, cheap poll (still holds)

**Abort.** `ChatApi.get(chatId, options?: { signal?: AbortSignal; ifNoneMatch?: string })` in `shared/src/chat.ts`; `ChatClient.get` passes the signal to `requestJson` (which already merges it with its timeout via `AbortSignal.any`). `chat-runtime.tsx` `refreshTree` passes the poll's signal (today it only checks `signal.aborted`). **RED:** unmounting during an in-flight poll leaves `init.signal.aborted === true`.

**Validator — what it is computed from.** The brief allows no schema change besides item 5, so there is no revision column and no trigger. The validator is one aggregate query over the same rows the tree query reads, using only columns that every tree-changing write already updates:

| Tree part                                                     | Validator input                                                                                                           | Why it changes                                                                                                                                            |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| title, viewed leaf, chat row                                  | `c.updated_at`, `c.title_version`, `c.viewed_leaf_id`, `c.title` (hashed)                                                 | `rename`, `applyTitle`, `selectLeaf` and the terminal-pointer trigger bump `updated_at`; leaf and title are included directly, so no reliance on the bump |
| messages, branches                                            | `count(*)`, `max(created_at)`, `max(id::text)` over `chat_messages` of the chat                                           | messages are insert-only (trigger `ai_chat_message_tree_guard`); any insert changes the count                                                             |
| run status, final output, partial output, reasoning           | per linked run: `run_version`, `status`, `updated_at` (aggregated as `count`, `sum(run_version)`, `max(updated_at)`)      | `transition` bumps `run_version`; output and checkpoint-pair writes bump `updated_at`                                                                     |
| streamed checkpoint text                                      | `count(*)`, `max(created_at)` over `ai_checkpoints` of the linked runs                                                    | the upsert sets `created_at = clock_timestamp()`                                                                                                          |
| live-step gate (lateral join on claimed step, active attempt) | `max(updated_at)` of `ai_steps`, and `count(*) FILTER (active)` + `max(settled_at)` of `ai_attempts`, for the linked runs | a claim or settle can change the lateral join without touching `ai_runs`                                                                                  |
| feedback                                                      | `count(*)`, `max(updated_at)` over `message_feedback` of the chat                                                         | an upsert bumps `updated_at`; clearing a rating deletes the row, which changes the count                                                                  |

The ETag is `W/"<base64url(sha-256(tuple))>"`, prefixed with a format version (`v1`) so a future input change invalidates old tags. The tag is weak because it stands for semantic equivalence, not for the exact bytes. RFC 9110 §13.1.2 requires weak comparison for `If-None-Match` anyway.

**Proof it changes on every tree change.**

1. Per-kind tests (brief): new message, new branch (edit/regenerate), run status, final output, checkpoint, feedback set/change/clear, viewed leaf, title. Each is applied through the real repository or service path and must give a new ETag and a 200.
2. **Completeness test (lifecycle):** drive a real chat through a full run (send → claim → checkpoints → complete → feedback → edit branch → select leaf → rename → regenerate → cancel). After every write, record `(etag, tree)`. Assert that whenever two consecutive trees differ (deep equality), the ETags differ. This catches a tree change the table above misses.
3. **Coverage guard:** a unit test lists the columns that `ChatMessageRepository.tree` selects, as an explicit constant, against the validator's input map above. Adding a tree column without a validator input fails the test.

The microsecond `clock_timestamp()` values plus counts and `run_version` make a false 304 require two writes to the same table in the same microsecond with an unchanged count — not reachable through the app's serialised per-chat writes.

**Read before the tree query.** In `ChatService.get`, inside the same `withTenant` transaction:

1. `readLive` (ownership, RLS) → absent → `CHAT_NOT_FOUND` (the safe 404), whatever `If-None-Match` says.
2. `readTreeValidator(tx, chatId)` → ETag.
3. If `If-None-Match` weakly matches the ETag (or is `*`) → return `{ notModified: true, etag }`; `messages.tree` is not called.
4. Otherwise run `messages.tree` and return `{ tree, etag }`.

`withTenant` opens a plain `BEGIN`, so the transaction is READ COMMITTED and the validator and the tree query do **not** share one snapshot (owner amendment 3). The order is what makes it safe: the validator is read first and the tree second, so the body is never older than its tag. A write between the two reads gives a body newer than the tag; the worst case is one extra 200 on the next poll, never a stale tree kept by a 304. A test pins the order: with spies on both repository calls, the validator query runs before the tree query (`mock.invocationCallOrder`). **RED:** a service test with a spy on `ChatMessageRepository.tree` and a matching tag expects 304 and zero calls (today: always 200 and one call).

**HTTP.** The controller reads `If-None-Match` and uses `@Res({ passthrough: true })` to set `ETag` and `Cache-Control: no-store` on both the 200 and the 304 (owner amendment 4: the body is K1 and must not be kept in the browser cache; conditional polling still works because the client sends `If-None-Match` itself). No `Vary` header. The HTTP test asserts these headers on both responses. A 304 has no body (`res.status(304).end()`). Express's own body-hash ETag is turned off for this route by setting the header ourselves; to be sure, the controller sets it before the body is sent, and a test asserts the returned tag equals the validator tag, not a body hash. The body of the 200 is unchanged.

**Foreign actor.** Ownership runs first, so a cross-user or cross-org request with the owner's ETag gets the same 404 body as a random id, and never a 304. **RED/guard:** an integration test (real identities, real HTTP) for both actors.

**Client.** `use-tree-polling` keeps the last ETag and sends it as `If-None-Match` (`requestJson` already uses `cache: 'no-store'`, which per WHATWG Fetch returns the raw 304 to the caller). On 304 the client keeps the current tree object and makes no state update. The first load and a refresh that a stream frame asks for may send no tag. **RED:** a frontend test where a 304 tick keeps the same tree object (`Object.is`) and triggers no render of the tree consumer.

**Logging (owner amendment 7).** The ETag is derived from K1 (its hash includes the title). The ETag and `If-None-Match` values are never logged. If any log path includes request or response headers (pino-http serializers, the error filter), both headers are added to its redaction, with a test that a logged request carries neither value.

**Query cost record (owner amendment 6).** On a large synthetic chat (500 messages, 50 runs, with checkpoints and feedback), record `EXPLAIN (ANALYZE, BUFFERS)` and the timing of the validator query and of the tree query, and show that the validator uses indexes (no sequential scan on the chat's child tables). This is a record, not a threshold. If the validator is not clearly cheaper than the tree query, stop and ask the owner.

**Evidence:** the four brief tests, the order test, the lifecycle completeness output, a sample 200/304 header pair, and the query cost record.
