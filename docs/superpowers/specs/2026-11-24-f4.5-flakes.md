## Item 1 — TOTP enrollment E2E (`account-security.spec.ts:238`)

**Root cause (hypothesis, high confidence — the RED below proves it).** A
pre-hydration click on "Use a recovery code" is silently dropped. Evidence:

- Symptom (both runs): `locator.fill` waited the rest of the 45 s
  whole-test timeout for `getByLabel('Recovery code', { exact: true })`
  after clicking "Use a recovery code" (`:235-237`).
- `frontend/src/components/auth/two-factor-challenge.tsx:40-47`: the toggle
  is a plain `type="button"` outside the form with
  `onClick={() => setRecovery(v => !v)}` — a pure client state update. A
  click dispatched before React hydration has no handler bound and is a
  silent no-op (no native POST — unlike the `method="post"` auth forms from
  the F4.2 invitation-entry flake). With the click lost,
  `AuthenticationCodeForm` never remounts with `recovery`, so the
  `FormInput label="Recovery code"` (`authentication-code-form.tsx:69-74`)
  never renders.
- The page is SSR'd (`frontend/src/app/(auth)/two-factor/page.tsx` — button
  is actionable while still unhydrated). `await
expect(page).toHaveURL(/two-factor/)` at `:231` resolves at navigation
  commit; the only delay before the click is one `page.request.get`
  (`:233`). The frontend container is capped at 0.5 CPU / 256 MiB
  (`docker-compose.yml`), so the commit->hydrate window stretches under CI
  load.
- `account-security.spec.ts` never calls `waitForHydration`
  (`backend/test/e2e/identity-support.ts:42-52`, polls `__reactProps$*` —
  works in production builds); every other spec touching SSR'd auth forms
  does. The file predates the convention (last touched `960d6ab1`, F4.1).

**Evidence that would prove it:** the retained trace (see task 1) shows the
click dispatched while the button lacks `__reactProps$*`, no state change,
no request fired. A hydrated-but-late click renders the input in the same
commit, so a multi-second no-show already rules out "slow render".

**RED (deterministic):** delay hydration past the click — `page.route` the
`/_next/static/**` chunk requests with a multi-second stall before the
`/sign-in` submit, so `/two-factor` commits but does not hydrate; click
lands pre-hydration; `getByLabel('Recovery code')` never appears — same
failure. Proven equivalent to the F4.2 mechanism reproduction ("JS held
until after the click").

**Fix (test only, no product change):** `await waitForHydration(
page.getByRole('button', { name: 'Use a recovery code', exact: true }))`
before the click at `:236`. Same guard before the "Set up authenticator"
click at `:162` — the `/workspace?settings=security` page is also SSR'd and
that click is the same class (prevents the sibling recurrence inside the
20-pass round). No assertion changes.

**Acceptance evidence line (for `docs/references/F4.5-acceptance.md`):**
`item 1: RED via delayed hydration reproduced the swallowed click;
waitForHydration added on the two-factor toggle and the authenticator setup
click (test only); flake-round <run URL> 20/20.`

## Item 2 — open sign-up navigation race (`platform-setup-open-signup.spec.ts:169`)

**Root cause (hypothesis, high confidence).** The ordinary user's
post-sign-in `window.location.assign('/workspace')` is still in flight when
the test calls `page.goto`. Evidence:

- Log line (run 45235041821): `page.goto: Navigation to
"…/platform/provisioning" is interrupted by another navigation to
"…/workspace"`.
- `frontend/src/components/auth/login-form.tsx:86-100`: on successful
  sign-in the client does `window.location.assign(next)` — a full
  cross-document navigation, `next` defaulting to `/workspace`
  (`frontend/src/lib/return-path.ts`). This is the exact URL that
  interrupted the goto.
- `signInThroughForm` (`platform-setup-open-signup.spec.ts:24-37`) waits
  only for the `POST /api/auth/sign-in/email` 200 — never for the resulting
  navigation. The first call site is protected by
  `await expect(page).toHaveURL(/admin-setup/)` (`:76`); the second call
  site (`:158`) is followed only by two API-context requests
  (`ordinary.request.get`, not page waits) then the failing `goto` (`:169`).
- `/workspace` SSR passes `proxy.ts` and the layout awaits
  `loadWorkspaceBootstrap()` — a server-side API call on the 0.5-CPU
  frontend container — so the navigation can still be pending seconds
  later. (A `Workspace` client `router.replace('/onboarding')` for
  non-onboarded users is a second possible pending nav; the reported
  competing URL was `/workspace`, matching the assign.)

**Evidence that would prove it:** the trace shows `GET /workspace` issued
after the sign-in 200 and still pending when `goto` was issued. Both
variants are fixed by the same wait.

**RED (deterministic):** `page.route` the `GET /workspace` document request
with a multi-second stall; after `signInThroughForm` the assign is still in
flight; `page.goto('/platform/provisioning')` is interrupted — same error.

**Fix (test only):**

1. After `signInThroughForm(ordinaryPage, …)` at `:158` add
   `await expect(ordinaryPage).toHaveURL(/\/(workspace|onboarding)/)` —
   the convention already used at `platform-console-browser.spec.ts:584`,
   `platform-identity.spec.ts:603`, `invitation-entry.spec.ts:103`. The
   `toHaveURL` resolves only when the in-flight navigation commits, so the
   later `goto` cannot be interrupted.
2. Uniquify the fixed emails so the test is idempotent on a kept stack —
   required for the 20-pass flake round on one stack:
   `open.setup.operator@example.test` (`:45`) and
   `open.ordinary.user@example.test` (`:136`) become
   `randomUUID() + '@example.test'` (pattern already used at
   `account-security.spec.ts:115`). Assertions unchanged
   (`setup.status === 'created'`, `created.ok()` both stay true on fresh
   addresses).

**Acceptance evidence line:** `item 2: RED via delayed /workspace document
reproduced the interrupted goto; signInThroughForm call site now waits for
the post-sign-in URL and both fixture emails are unique (test only);
flake-round <run URL> 20/20.`

## Item 3 — `ai-cancel.spec.ts` (`:207` and `:786`)

**Root cause (sufficient mechanism, reproduced by RED; CI logs carry no
direct deadline evidence — the log shows the two assertion signatures, not
the elapsed deadline).** The 250 ms per-publication deadline
(`DEFAULT_PUBLICATION_DEADLINE_MS`,
`run-streams.ts:129`) is crossed on a loaded CI runner — the exact vector
audit item A-13 fixed for `ai-streams.spec.ts` (`publicationDeadlineMs:
2000`, `ai-streams.spec.ts:2567`) but never applied here; the file predates
the option. `ai-cancel.spec.ts` has three `new RunStreams(…)` sites (`:189`,
`:693`, `:1350`), all with the default.

- `:207` — `streams.publish(claim, {type:'start'})` must finish
  lazy-connect (`connectTimeout` alone is 500 ms,
  `run-streams.ts:154-162`) + `TIME` + epoch `GET` + two `streamActiveProof`
  DB transactions + `EXISTS`/`ZSCORE`/`ZRANGE` + `PREPARE` + `APPEND` — ~12
  round-trips inside one 250 ms envelope measured from `publish()` entry.
  Any slow hop returns `'unavailable'` (`run-streams.ts:212,515-519,565,
608-613`). `'unavailable'` is exclusively the "dependency too slow"
  bucket; `'stale'` is a different code path.
- `:786` — `['reset','start','status','finish']` is produced **only** by
  `FINISH_RUN_STREAM` with `ARGV[14]=='1'` (`run-stream-scripts.ts:236-243`)
  — `resetToSnapshot: true`, which `StepExecutor.#finishIfTerminal` passes
  only when `streamSnapshotRequired` is armed
  (`step-executor.ts:2034-2055`), i.e. some earlier publish returned
  `'unavailable'` — most likely `streams.recover()` at
  `step-executor.ts:338`, the first command on that lazy client. Same 250 ms
  deadline, same mechanism. The product behaviour (re-snapshot on possibly
  lost framing) is degraded-but-correct by design; only the tests' strict
  happy-path timing assumption is wrong for a loaded runner.

**RED (deterministic):** temporarily set `publicationDeadlineMs: 1` on the
spec's `RunStreams`: `:207` returns `'unavailable'` deterministically, and
`:786` deterministically ends `['reset','start','status','finish']` via the
armed `streamSnapshotRequired` path — both CI signatures reproduced.
Reverted after recording (scratch-RED convention; an injected one-shot
~300 ms delay in `authority.authorizeActive` is the equivalent alternative
if the 1 ms deadline proves flaky in setup).

**Fix (test only):** `publicationDeadlineMs: 2000` in all three
`new RunStreams(…)` constructions (`:189`, `:693`, `:1350`) — the accepted
A-13 remedy. No assertion changes; product untouched.

**Acceptance evidence line:** `item 3: RED via publicationDeadlineMs: 1
reproduced both CI signatures; publicationDeadlineMs: 2000 on the spec's
RunStreams (the A-13 pattern, test only); flake-round <run URL> 20/20.`

## Item 4 — S2 burst ramp peak (`chat-sse-load.z-burst.spec.ts:450`)

**What is established (from run `45241596238` + code):**

- The gauge is a **running maximum** over an `open` set: `peak =
max(peak, open.size)` updated inside a `writeHead` patch on every
  `content-type: text/event-stream` response, decremented on the response
  `'close'` (`backend/test/load/burst-harness.mjs:153-206`, patched in
  `chat-load-api-main.mjs`). Sampling is effectively continuous until the
  metrics read.
- `admitted = 500` means every client's response emitted `writeHead` + a
  frame — all 500 were gauge-opened. **`peak < 500` therefore requires
  > =16 counted streams to have closed before the last stream opened.** The
  > brief's alternatives "counted late" and "gauge samples a moment when
  > streams are not yet registered" are refuted by the running-max design;
  > "clients aborted mid-connect" is also refuted — a pre-`writeHead` abort
  > has no gauge entry and would show as `admitted < 500`.
- The counters are **incomplete in this spec**: `recordClose` call-sites
  are all gated on `ownerIndex`, which only `set-owners`/`set-load-runs`
  populate — and `z-burst.spec.ts` never calls them (only the F4.1 spec
  does). So the only reachable counter is `onResponseClose`'s
  `clientAbort`, which early-returns when `writableFinished === true`.
  Every server-initiated close (`sink.close(reason)` -> `res.end()` for
  `revoked`/`evicted`/`slowClient`/`shutdown`, and error-filter
  `res.status().json()` post-headers) ends `writableFinished` and records
  **nothing**. `close` events still queued when the `burst-metrics` reply
  is written also miss the snapshot — no server-side drain barrier before
  `metrics.sse` is read (`z-burst.spec.ts:402`). Even green run B recorded
  only 316/382 closes.

**Leading hypothesis for the early closes (to be named by the completed
counters, not assumed):** renewal churn inside the 1 s renewal tick
(`run-events.service.ts:322-343`) while the event loop + auth pool are
starved (`authPoolWaitP95` 2.1-2.5 s, `poolWaitingMax` 210-374 vs ~0.5 s /
~98-112 on green ramps): `registry.renew` rejecting -> `close('revoked')`
(registry client `commandTimeout` 1 000 ms, `enableOfflineQueue: false`,
`maxRetriesPerRequest: 0`, `sse-connection-registry.ts:97-104`), or `renew`
returning falsy -> `close('evicted')` (`leaseMs` 3 000 ms — a >2 s stall
lets the lease expire, `:94`). Runner-up: `slowClient` on the 15 s
heartbeat's `drain(5000)` under backpressure. Burst is immune because all
500 open within ~5-9 s — the peak forms before a full 30 s churn window
elapses.

**RED (deterministic, harness unit test):** a counter test that fails
today — a gauge-counted stream whose response `'close'` arrives with
`writableFinished === true` records no reason (server-initiated close
invisible), and a counted-open stream closed during teardown after the
metrics reply records nothing. RED shows the current counters cannot tell
a server close from a client abort.

**Fix part A (harness only, `backend/test/load/close-counters.mjs` +
`chat-load-api-main.mjs` + `burst-harness.mjs`):** make the counters
complete — **every stream the gauge counts records exactly one close
reason.** No stream records zero, and no stream records two:

1. Classify every counted `'close'` by `writableFinished`
   (`clientAbort` vs `serverEnd`/`finished`) in `onResponseClose` —
   distinguishes server-end from client abort without `ownerIndex`.
2. Ungate `recordClose` where it names service reasons (invalidation sink
   wrapper and hub `subscribe` proxy) so `revoked*`/`evicted`/`slowClient`
   are attributed even without `ownerIndex` (which is only needed for
   revoked-cause detail).
3. Exactly one reason per stream: when the ungated service-reason
   `recordClose` has already recorded a reason for a stream, the later
   `writableFinished` classification in `onResponseClose` must not add a
   second one — first reason wins. Add a counter test for that case
   (`scripts/test/chat-load-close-counters.spec.mjs`).
4. `burst-metrics` returns `openedTotal`/`closedTotal` (and elapsed of last
   open) so `closedTotal` before last-open directly proves the peak loss.
5. A bounded close-drain barrier before the metrics read: poll
   `closedTotal >= openedTotal` up to a stated bound (e.g. 10 s); when the
   bound expires the step fails reporting the missing count
   (`openedTotal - closedTotal`). It never passes silently.
   The assertion "every counted stream has exactly one close reason" is
   asserted in the close-counters spec
   (`scripts/test/chat-load-close-counters.spec.mjs`).

**Fix part B (cause, product or harness — decided by the completed
counters on run 1):**

- If early closes are `evicted`/`revoked` renew-related: candidate product
  hardening (renewal/lease margin under stall) — **stop for the owner if
  the change is user-visible**; a harness-side alternative is none — the
  ramp pacing is the thing under test and must not change.
- If `slowClient`: drain/backpressure margin or harness read pacing —
  decide per evidence.
- **If the cause is pool contention that only B-02 can fix: stop and
  report to the owner** (brief rule).
- If no early closes reproduce under complete counters (as in instrumented
  run A), the complete counters + `openedTotal`/`closedTotal` stand as the
  diagnosability fix and the residual is recorded for the owner.

**chat-sse-load run plan (cap 2):** the counter-completeness commit touches
`backend/test/load/**` and `backend/test/e2e/chat-sse-load.z-burst.spec.ts`
— both in `chat-sse-load.yml` `paths:` — so the first code push fires run 1
automatically. Run 2 is the post-fix proof (push or `workflow_dispatch`).
No other runs.

**Acceptance evidence line:** `item 4: counters made complete (RED: counted
close with writableFinished recorded nothing); run <URL> counters name the
early-close reason as <reason>; fix <or owner stop report>; final
chat-sse-load <run URL> 500/500 with every counted stream carrying one
close reason.`

   overridden and stays at the production default `account: 5, ip: 30,
windowSeconds: 300` (`auth-rate-config.ts:31`). 20 iterations cannot
   cross these: each iteration spends ~1 `signup`, ~2-3 `signin`, ~3-4
   `totp` and ~1 `recovery` call against a **fresh** account (account

   only shared constraint — at ~1-3 iterations/minute a rolling 300 s
   window holds ≤ ~10 `totp` and ≤ ~10 `recovery` calls against limits of
   100 and 30, and `signin` (60 s window) sees ~5 against 100. No limit is
   disabled or weakened; the loop stays inside them as configured.
