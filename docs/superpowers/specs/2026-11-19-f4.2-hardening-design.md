## 1. Intent

The goal is to make F0–F4.1 solid before F5 builds on them. This slice adds no features and no screens. Users get:

- precise failures (409 and 503 instead of 500 or 404);
- a chat client that polls less and streams smoothly;
- failures that are never shown as empty lists.

Engineers get:

- a repository without retired design material;
- deterministic tests;
- an S2 load proof under realistic conditions;
- a shorter CI.

**Goals:** brief items 1–30, in the order in §3.

**Non-goals:** the brief's out-of-scope table (A-06, A-11, A-18, A-20, A-21, A-23, A-24, F4.3 modules, and a larger chat-state refactor).

**Anti-goals.** The slice fails, even if every test is green, if any of these happens:

- a response reveals more than today (a foreign or missing resource stays 404);
- an assertion is weakened;
- a golden changes without owner approval;
- a test is quarantined or retried instead of fixed;
- Docker hygiene is broken.

## 2. Approaches

| Approach                                                                                | Trade-off                                                                                                                             | Verdict                                                                        |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **A. One branch, 8 sequential tasks in the brief's order, with a draft PR from Task 1** | CI checks every push. Task 1 shrinks the repo before anything else is touched. Long-lived branch.                                     | **Chosen.** The brief prescribes the order and a draft PR from the first task. |
| B. Split into 3 PRs (cleanup / backend / client + CI)                                   | Smaller reviews, but three rounds of S2 and visual gates. Budget mode allows at most 2 Linux rounds per area.                         | Rejected: it multiplies Linux rounds.                                          |
| C. Do CI sharding first, to speed up later tasks                                        | Faster feedback earlier. But sharding a suite that Task 1 is about to change means doing it twice, and the owner fixed sharding last. | Rejected.                                                                      |

## 3. Task order and design per item

Every rule is test-first. The planned RED evidence is the named test failing on the current `main` behavior, with its output tail recorded in `docs/references/F4.2-acceptance.md` (one short record per task). Timing, load, and visual evidence come from Linux.

## 4. Settled decisions (owner spec review, 2026-11-19; brief decisions 6–11)

- **A-04 (decision 9).** The design is the shared 1 s single-flight cache, a 5 s interval, and an auth pool of 10. The Linux burst at the Compose limits decides; the semaphore is a fallback only.

  Evidence for this choice: a local measurement on 2026-11-19 (Postgres 17, `pg` 8.23.1, 500 concurrent 5 ms queries).

  | Pool max | Succeeded  | p95 acquire wait |
  | -------- | ---------- | ---------------- |
  | 5        | 500 of 500 | 616 ms           |
  | 10       | 500 of 500 | 296 ms           |
  | 20       | 500 of 500 | 154 ms           |

  A one-shot burst does not reach the timeout. The failure comes from sustained uncached checks, and pg-pool already queues waiters without a limit (R2b).
