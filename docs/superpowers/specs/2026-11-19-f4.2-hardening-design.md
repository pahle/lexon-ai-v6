## 1. Intent

The goal is to make F0–F4.1 solid before F5 builds on them. This slice adds no features and no screens. Users get:

- precise failures (409 and 503 instead of 500 or 404);
- a chat client that polls less and streams smoothly;
- failures that are never shown as empty lists.

Engineers get:

- a repository without retired design material;
- deterministic tests;
- an S2 load proof under realistic conditions;
- a shorter CI.

**Goals:** brief items 1–30, in the order in §3.

**Non-goals:** the brief's out-of-scope table (A-06, A-11, A-18, A-20, A-21, A-23, A-24, F4.3 modules, and a larger chat-state refactor).

**Anti-goals.** The slice fails, even if every test is green, if any of these happens:

- a response reveals more than today (a foreign or missing resource stays 404);
- an assertion is weakened;
- a golden changes without owner approval;
- a test is quarantined or retried instead of fixed;
- Docker hygiene is broken.

## 2. Approaches

| Approach | Trade-off | Verdict |
|---|---|---|
| **A. One branch, 8 sequential tasks in the brief's order, with a draft PR from Task 1** | CI checks every push. Task 1 shrinks the repo before anything else is touched. Long-lived branch. | **Chosen.** The brief prescribes the order and a draft PR from the first task. |
| B. Split into 3 PRs (cleanup / backend / client + CI) | Smaller reviews, but three rounds of S2 and visual gates. Budget mode allows at most 2 Linux rounds per area. | Rejected: it multiplies Linux rounds. |
| C. Do CI sharding first, to speed up later tasks | Faster feedback earlier. But sharding a suite that Task 1 is about to change means doing it twice, and the owner fixed sharding last. | Rejected. |

## 4. Open questions — recommendations

**Q1 A-22: keep `SECURITY DEFINER` and document the true invariant.**

The brief's premise is half-true. `lexon_app` has direct `INSERT` on `ops.audit_events` (`0005_audit.sql:17`), but `lexon_auth` does **not**: line 16 revokes all from it, and it writes audit rows only through the function (`auth-transaction.ts:129`).

So `SECURITY INVOKER` would break auth-side auditing, unless we also grant `INSERT` to `lexon_auth`. That would widen privilege.

**Recommendation:** a migration comment on `auth.lexon_append_audit`, plus one guard added to the function body:

- the comment states that for `lexon_app` the function adds no privilege, and for `lexon_auth` it is the only write path;
- the guard: when `session_user = 'lexon_app'`, require that the event's organization equals the current tenant GUC.

This makes the brief's test ("`lexon_app` cannot write an audit row for another organization through the function") pass. Today it would **fail**: the function only validates shape.

Note that `lexon_app` can still direct-INSERT a foreign-organization row, because `ops.audit_events` has no RLS (see §6, Q6).

This is a function change, so it is one migration. The brief allows a migration only for INVOKER, so I need the owner's approval to deviate.

**Q2 A-04: cache plus a 5 s interval as the fix, the pool raised from 5 to 10, and no new admission queue.**

Local measurement (2026-11-19, Postgres 17 container, `pg` 8.23.1, 500 concurrent 5 ms queries):

| Pool max | Succeeded | p95 acquire wait |
|---|---|---|
| 5 | 500 of 500 | 616 ms |
| 10 | 500 of 500 | 296 ms |
| 20 | 500 of 500 | 154 ms |

A one-shot burst never reaches the 10 s timeout. The failure is the **sustained** load: 500 streams × 1 uncached check per second against 5 connections. The waits grow unbounded. pg-pool already queues waiters without a limit (R2b), so "queued admission" exists already and is what times out.

The cache plus single-flight plus the 5 s interval cut demand by about 5× or more. Raising the pool to 10 halves the burst wait for little memory (Postgres `max_connections` headroom is checked in the plan).

Adding our own admission queue adds code without addressing the root cause. If the Task 5 burst still fails, the second Linux round adds a bounded semaphore.
