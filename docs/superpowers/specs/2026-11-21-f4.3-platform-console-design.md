## 1. Intent

Platform administrators need to find and support accounts and organizations
without pasting IDs, and without ever seeing organization content. Two modules,
**Accounts** and **Organizations**, replace Account status and Provisioning.
Success: an administrator can search, read the state of an account or an
organization at a glance, and run the brief's actions; every action is audited;
the API enforces every limit; responses carry only the contracted fields.

**Goals:** the brief's items 1–11 and acceptance criteria.
**Non-goals:** everything in the brief's Out of scope table (suspend/delete,
owner change on active orgs, audit views, usage, exports, personal workspaces).
**Anti-goals (failure even if it works):** any K1 content or session
device/IP data in a response, log, or trace; a read path that `lexon_app` can
reach; a refusal that exists only in the UI; a failure rendered as empty; search
terms in logs.

## 2. Current state (read on 2026-11-21, main @ origin)

- Platform mutations run in `OrganizationAuthPort.platformTransaction`
  (`backend/src/modules/identity-access/organization-auth.port.ts:48`) on the
  `lexon_auth` connection: it re-reads security facts, requires the platform
  role with 2FA (`IdentityPolicy.requireAccount(..., { platform: true })`), and
  requires recent re-authentication (`reauthSeconds`).
- `PATCH /api/platform/users/:userId/disabled` calls the Better Auth admin
  plugin `banUser` / `unbanUser` and appends `platform.user_disabled_changed.v1`
  (`platform-admin.service.ts`).
- The admin plugin is configured with `admin: { user: ['ban'], session: ['revoke'] }`
  (`auth-factory.ts:261`); the bearer plugin is enabled; Better Auth's own rate
  limiter is off (`rateLimit: { enabled: false }`), and Lexon rate-limits auth
  actions with `AuthLimiter` (Valkey, `rate-limiter-flexible`), including a
  `verification-resend` action at 3 per account / 10 per IP per 600 s
  (`config/auth-rate-config.ts:26`).
- All identity tables (`auth.user`, `auth.session`, `auth.member`,
  `auth.organization`, `auth.invitation`, `auth.two_factor`) live in schema
  `auth`; `lexon_auth` holds table DML there by default privileges; `lexon_app`
  has no usage on `auth`. Narrow `SECURITY DEFINER` functions in `auth` with
  `SET search_path=pg_catalog,auth,pg_temp` and explicit `GRANT EXECUTE`
  already exist (0013, 0014).
- Provisioning routes return 403 `ORG_FORBIDDEN` for unknown organizations
  today. Shared error codes contain no generic "not found" outside chat
  (`CHAT_NOT_FOUND`); see Q2.
- Frontend: `/platform/accounts` (Account status form by user ID),
  `/platform/provisioning`, `/platform/provisioning/[orgId]`,
  `components/platform/*`. shadcn `base-nova` components already installed:
  `table`, `dialog`, `alert-dialog`, `badge`, `empty`, `input`, `skeleton`,
  `sonner`, `select`.
- `pg_trgm` is installed (`0000_foundation_roles.sql:13`).

## 3. Approaches for the cross-organization read path

| | Approach | Trade-off |
|---|---|---|
| A | **Narrow `SECURITY DEFINER` read functions** in schema `auth`, owned by the migration owner, `REVOKE ALL ... FROM PUBLIC`, `GRANT EXECUTE` to `lexon_auth` only. Each returns exactly the contract projection. | Matches F1 style; projections are enforced in SQL so a column like `session.ip_address` can never be selected by the platform path; one migration per change. **Chosen.** |
| B | New `NOLOGIN` role `lexon_platform_read` with column-level `SELECT` grants, `SET ROLE` inside the platform transaction. | Column grants are fine-grained but `SET ROLE` from `lexon_auth` needs membership, which widens `lexon_auth`; aggregates and cursor logic live in TypeScript. |
| C | Plain Drizzle queries on the `lexon_auth` connection. | No new grants, but nothing in the database limits which columns are read; does not satisfy the brief's "narrow path". |

**Decision: A.** Reads do not widen `lexon_app` or `lexon_auth` table grants;
they add only `EXECUTE` on six functions to `lexon_auth`.

## 4. Backend design

### 4.1 Read functions (migration `0040_platform_console.sql`)

All `LANGUAGE sql STABLE SECURITY DEFINER SET search_path=pg_catalog,auth,pg_temp`,
`REVOKE ALL ON FUNCTION ... FROM PUBLIC`, `GRANT EXECUTE ... TO lexon_auth`.
Every function takes `lim int` (validated 1–100 by Zod; the function clamps
too) and a nullable `after uuid` cursor; it returns `lim + 1` rows so the
service can compute `nextCursor` without a count query.

| Function | Returns (columns) | Order / keyset |
|---|---|---|
| `lexon_platform_accounts(q text, lim int, after uuid)` | `id, name, email, status, two_factor_enabled, team_count, created_at, last_active_at` | `(created_at DESC, id DESC)`; cursor row resolved by `id` → `(created_at, id) < (c.created_at, c.id)` |
| `lexon_platform_account(uid uuid)` | summary columns + `email_verified, active_session_count` | single row or none |
| `lexon_platform_account_teams(uid uuid)` | `organization_id, name, slug, role` for `kind='team' AND state='active'` | `name, id` (unpaged; the number of teams per account is small) |
| `lexon_platform_organizations(q text, st text, lim int, after uuid)` | `id, name, slug, state, member_count, owner_email, created_at` for `kind='team'` | `(created_at DESC, id DESC)` |
| `lexon_platform_organization(oid uuid)` | summary + `require2fa` (active) or the provisioning invitation `id, status, expires_at` | single row or none |
| `lexon_platform_members(oid uuid, lim int, after uuid)` | `user_id, name, email, role, joined_at` | `(member.created_at ASC, user_id ASC)`; cursor is the last `userId` |

Derivations (all in SQL):

- `status`: `banned` → `disabled`; else `NOT email_verified` → `unverified`; else `active`.
- `team_count`: count of `member` rows in `kind='team' AND state='active'` organizations.
- `active_session_count`: sessions with `expires_at > now()` and (`hard_expires_at IS NULL OR hard_expires_at > now()`).
- `last_active_at`: see §4.4.
- `owner_email`: active → email of the owner member with the earliest `member.created_at`; provisioning → the pending owner invitation's email.
- Search: `q IS NULL OR lower(name) LIKE '%'||esc(lower(q))||'%' OR lower(email) LIKE ...` (orgs: name or slug); `%`, `_`, `\` escaped in TypeScript and with `ESCAPE '\'`.
- Platform-administrator flag: not returned (see Q1).

Indexes (same migration):

- `user_created_at_id_idx ON auth."user"(created_at DESC, id DESC)`
- `user_name_trgm_idx`, `user_email_trgm_idx`: `GIN (lower(name) gin_trgm_ops)`, `GIN (lower(email) gin_trgm_ops)`
- `organization_team_created_idx ON auth.organization(created_at DESC, id DESC) WHERE kind='team'`
- `organization_name_trgm_idx`, `organization_slug_trgm_idx` (GIN trigram on `lower(...)`)
- `member_org_created_idx ON auth.member(organization_id, created_at, user_id)`; `member_user_idx ON auth.member(user_id)` if not already present
- `session_user_expires_idx ON auth.session(user_id, expires_at)` if not already present

### 4.2 Routes, guards, schemas

New `PlatformConsoleModule` (backend `modules/platform-console`), controllers
under `/api/platform`, all `@PlatformRoute()` (anonymous 401, non-admin 403
`ORG_FORBIDDEN`, admin without 2FA 403 `ORG_FORBIDDEN`, as today). Reads run in
a new `OrganizationAuthPort.platformRead` that re-checks the platform policy
like `platformTransaction` but does **not** require re-authentication (my
call: reads are not sensitive actions; mutations keep re-authentication as
today). Reads and mutations use the authenticated API rate limit.

Strict Zod schemas in `shared/src/platform.ts` (exported from `@lexon/contracts`).
Every field is from the brief's table; nothing is added.

```ts
export const PlatformAccountStatusSchema = z.enum(['active', 'unverified', 'disabled']);
export const PlatformSearchSchema = z.string().trim().min(2).max(100);
export const PlatformAccountsQuerySchema = PaginationSchema.extend({
  query: PlatformSearchSchema.optional(),

export const PlatformAccountSummarySchema = z.strictObject({

  createdAt: z.iso.datetime(), lastActiveAt: z.iso.datetime().nullable(),
});
export const PlatformAccountsPageSchema = pageSchema(PlatformAccountSummarySchema);
export const OrganizationRoleSchema; // reuse the existing owner|admin|member schema
export const PlatformAccountTeamSchema = z.strictObject({
  organizationId: UuidSchema, name: DisplayNameSchema, slug: TeamSlugSchema, role: OrganizationRoleSchema,
});
export const PlatformAccountDetailSchema = PlatformAccountSummarySchema.extend({
  emailVerified: z.boolean(),
  activeSessionCount: z.number().int().nonnegative(),
  teams: z.array(PlatformAccountTeamSchema),
});
export const PlatformOrganizationStateSchema = z.enum(['active', 'provisioning']);
export const PlatformOrganizationsQuerySchema = PaginationSchema.extend({
  query: PlatformSearchSchema.optional(),
  state: z.enum(['all', 'active', 'provisioning']).default('all'),
});
export const PlatformOrganizationSummarySchema = z.strictObject({
  id: UuidSchema, name: DisplayNameSchema, slug: TeamSlugSchema,
  state: PlatformOrganizationStateSchema,
  memberCount: z.number().int().nonnegative(),
  ownerEmail: z.string(), createdAt: z.iso.datetime(),
});
export const PlatformOrganizationsPageSchema = pageSchema(PlatformOrganizationSummarySchema);
export const PlatformOrganizationDetailSchema = z.discriminatedUnion('state', [
  PlatformOrganizationSummarySchema.extend({ state: z.literal('active'), requireTwoFactor: z.boolean() }),
  ProvisioningSummarySchema, // unchanged, state: 'provisioning'

export const PlatformMemberSchema = z.strictObject({
```

Query strings are coerced (`limit` via `z.coerce.number()` in the controller's
query wrapper, the same way existing paged routes do; verify in the plan).
The backend parses its own response with the schema before sending
(fail closed → 503), and contract tests assert `.strict()` rejection of any
extra key.

### 4.3 Actions and refusals (API-enforced)

All run inside `platformTransaction` (platform role, 2FA, re-auth), so the
refusal checks and the action share one transaction.

1. **Self refusal** (disable `true`, sessions revoke): `targetUserId === identity.userId`
   → 409, code per Q2 (proposed `PLATFORM_SELF_ACTION`). Enabling yourself is
   unreachable (a disabled admin cannot sign in) and is not special-cased.
   Better Auth's own `YOU_CANNOT_BAN_YOURSELF` stays as a second line.
2. **Last enabled platform administrator** (disable `true`): in the
   transaction, `SELECT ... FROM auth."user" WHERE role='admin' AND NOT coalesce(banned,false) FOR UPDATE`
   via a new `SECURITY DEFINER` function `lexon_platform_lock_enabled_admins()`
   returning the ids; if the target is the only one → 409 (proposed
   `PLATFORM_LAST_ADMINISTRATOR`). The row lock serialises two concurrent
   disables of the last two admins (tested with two parallel transactions).
   With the self refusal in place this can only happen when another admin is
   targeted while the actor is not enabled-admin-countable, i.e. defence in
   depth; it is still enforced and tested.
3. **Sign out everywhere:** Better Auth admin `revokeUserSessions({ body: { userId } })`
   (`internalAdapter.deleteUserSessions`). Bearer tokens are session tokens
   (the bearer plugin converts `Authorization: Bearer` into the session cookie),
   so deleting session rows revokes them. Lexon's `RevalidationCache` TTL is
   1 s, so other devices fail at their next request after at most 1 s (test:
   a bearer request and a cookie request for the target both get 401 after
   revoke). Per-target limit: new `AuthLimiter` action `platform-session-revoke`,
   5 per target account per 600 s → 429 `AUTH_RATE_LIMITED`. Audit
   `platform.user_sessions_revoked.v1`.
4. **Resend verification email:** read `email_verified` via
   `lexon_platform_account`; verified → 409 (proposed `PLATFORM_ALREADY_VERIFIED`);
   consume the target's existing `verification-resend` **account** bucket
   (shared with the user's own resends, so the admin cannot exceed the user's
   limit) → 429 `AUTH_RATE_LIMITED`; then call `auth.api.sendVerificationEmail({ body: { email } })`
   **without** the admin's headers. With headers Better Auth 1.7.14 compares the
   session user's email and throws `EMAIL_MISMATCH`; without a session it takes
   the anonymous branch (constant-time 500 ms floor, sends only to unverified
   users). The existing verification email template and expiry are unchanged.
   Audit `platform.verification_email_resent.v1`.
5. **Disable** keeps today's behaviour (`banUser` deletes the user's sessions).

### 4.4 Last active

`max(session.updated_at)` disappears once sessions are revoked or pruned, so
the design adds a Lexon-owned table `auth.lexon_user_activity(user_id uuid PK,
last_active_at timestamptz)` maintained by an `AFTER INSERT OR UPDATE OF updated_at`
trigger on `auth.session` (upsert `greatest(...)`). Backfill from existing
sessions in the migration. `lastActiveAt` is `null` for never-signed-in
accounts. (My call; the alternative, reading only live sessions, is listed in Q4.)

### 4.5 Audit

New event types (validator `auth.lexon_validate_audit` extended in 0040,
ids and metadata only, actor = platform admin, `organizationId` null unless
stated):

| Type | Subject | Metadata |
|---|---|---|
| `platform.user_sessions_revoked.v1` | `subjectUserId` | `{}` |
| `platform.verification_email_resent.v1` | `subjectUserId` | `{}` |
| `platform.organization_members_viewed.v1` | `organizationId` | `{ firstPage: boolean }` |

Members viewed is written for **every** members request (each page is a view),
in the same transaction as the read, never the listed user ids. Refused actions
(self, last admin, already verified, rate limited) are not audited as success;
they write the existing failure outcome only if the current audit design
already records platform failures (verify in plan; no new failure events).

### 4.6 Logging and privacy

`query` is redacted from request logs and OTel span attributes (extend the
existing redaction list; test asserts a search term never appears in captured
logs/spans). No session IP, user agent, or device name is selected by any
function.

## 5. Tests (TDD; backend first)

- **Database (integration, real Postgres):**
  - as `lexon_app`: `EXECUTE` on each of the seven new functions → `permission denied`; `USAGE` on `auth` still absent; `SELECT` on `auth.lexon_user_activity` denied.
  - as `lexon_auth`: functions return exactly the contract columns (column-name assertion).
  - personal organizations never appear; provisioning org owner email is the invitation email.
  - keyset: pages are disjoint and complete with equal `created_at` ties.
  - last-admin lock: two concurrent disables of the last two admins → exactly one succeeds.
  - activity trigger and backfill.
- **Scale check** (`backend/test/integration/platform-console-performance.spec.ts`, follows `chat-search-performance.spec.ts`): seed 10,000 accounts, 2,000 team organizations, members; `ANALYZE`; `EXPLAIN (FORMAT JSON)` for: first page, next page, search 2 chars, search ≥3 chars, org state filter, members page. Assert no `Seq Scan` on `user`, `organization`, `member` for ≥3-char searches and keyset pages. pg_trgm cannot extract trigrams from a 2-character pattern, so 2-character searches are allowed a bitmap/seq scan; the test records but does not fail on them (documented; at 10k rows this is bounded). p95 of the search request over 50 runs is written to the CI summary on Linux only, not gated.
- **API (e2e, HTTP):** for every route: anonymous 401, member 403, admin without 2FA 403, admin 2xx; strict schema parse of every response plus an assertion that the raw JSON has exactly the contract keys; 404 for unknown ids and personal org ids; self refusal on disable and revoke; last-admin refusal; verification 409 and 429 (4th call within window); revoke actually signs out cookie and bearer sessions; audit rows written with no member ids; rate limits; search term absent from logs.
- **Frontend:** component tests per state (§6), axe in both themes, Playwright flows from the brief's User flows 1–9, visual captures.

## 10. Calls I made (check while reading)

- Approach A (definer functions) for reads; reads skip re-auth, mutations keep it.
- `lastActiveAt` from a new activity table maintained by trigger.
- Verification resend shares the user's own `verification-resend` bucket; new `platform-session-revoke` limit 5 / 600 s per target.
- Members viewed is audited on every page request.
- Member ordering: joined date ascending; cursor = last `userId`.
- Account teams list includes only active team organizations.
- `/platform/provisioning` redirects to the Organizations list filtered to Provisioning.
- Search minimum 2, maximum 100 characters; a 1-character query is rejected by Zod (400 `VALIDATION_ERROR`) and the UI does not send it.
