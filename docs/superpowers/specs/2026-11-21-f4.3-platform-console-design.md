## 1. Intent

Platform administrators need to find and support accounts and organizations
without pasting IDs, and without ever seeing organization content. Two modules,
**Accounts** and **Organizations**, replace Account status and Provisioning.
Success: an administrator can search, read the state of an account or an
organization at a glance, and run the brief's actions; every action is audited;
the API enforces every limit; responses carry only the contracted fields.

**Goals:** the brief's items 1–11, decisions 7–9, and acceptance criteria.
**Non-goals:** everything in the brief's Out of scope table (suspend/delete,
owner change on active orgs, audit views, usage, exports, personal workspaces).
**Anti-goals (failure even if it works):** any K1 content or session
device/IP data in a response, log, or trace; a read path that `lexon_app` can
reach; a refusal that exists only in the UI; a failure rendered as empty; search
terms in logs.

## 2. Current state (read on 2026-11-21, main @ origin)

- Platform mutations run in `OrganizationAuthPort.platformTransaction`
  (`backend/src/modules/identity-access/organization-auth.port.ts:48`) on the
  `lexon_auth` connection: it re-reads security facts, requires the platform
  role with 2FA (`IdentityPolicy.requireAccount(..., { platform: true })`), and
  requires recent re-authentication (`reauthSeconds`).
- `PATCH /api/platform/users/:userId/disabled` calls the Better Auth admin
  plugin `banUser` / `unbanUser` and appends `platform.user_disabled_changed.v1`
  (`platform-admin.service.ts`).
- The admin plugin is configured with `admin: { user: ['ban'], session: ['revoke'] }`
  (`auth-factory.ts:261`); the bearer plugin is enabled; Better Auth's own rate
  limiter is off (`rateLimit: { enabled: false }`), and Lexon rate-limits auth
  actions with `AuthLimiter` (Valkey, `rate-limiter-flexible`), including a
  `verification-resend` action at 3 per account / 10 per IP per 600 s
  (`config/auth-rate-config.ts:26`).
- All identity tables (`auth.user`, `auth.session`, `auth.member`,
  `auth.organization`, `auth.invitation`, `auth.two_factor`) live in schema
  `auth`; `lexon_auth` holds table DML there by default privileges; `lexon_app`
  has no usage on `auth`. Narrow `SECURITY DEFINER` functions in `auth` with
  `SET search_path=pg_catalog,auth,pg_temp` and explicit `GRANT EXECUTE`
  already exist (0013, 0014).
- Provisioning routes return 403 `ORG_FORBIDDEN` for unknown organizations
  today. Shared error codes contain no generic "not found" outside chat
  (`CHAT_NOT_FOUND`), but the platform error filter already maps a 404 to the
  generic safe code `NOT_FOUND` (`backend/src/modules/platform/error.filter.ts:175`).
- Frontend: `/platform/accounts` (Account status form by user ID),
  `/platform/provisioning`, `/platform/provisioning/[orgId]`,
  `components/platform/*`. shadcn `base-nova` components already installed:
  `table`, `dialog`, `alert-dialog`, `badge`, `empty`, `input`, `skeleton`,
  `sonner`, `select`.
- `pg_trgm` is installed (`0000_foundation_roles.sql:13`).

## 3. Approaches for the cross-organization read path

|     | Approach                                                                                                                                                                                                       | Trade-off                                                                                                                                                                 |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A   | **Narrow `SECURITY DEFINER` read functions** in schema `auth`, owned by the migration owner, `REVOKE ALL ... FROM PUBLIC`, `GRANT EXECUTE` to `lexon_auth` only. Each returns exactly the contract projection. | Matches F1 style; projections are enforced in SQL so a column like `session.ip_address` can never be selected by the platform path; one migration per change. **Chosen.** |
| B   | New `NOLOGIN` role `lexon_platform_read` with column-level `SELECT` grants, `SET ROLE` inside the platform transaction.                                                                                        | Column grants are fine-grained but `SET ROLE` from `lexon_auth` needs membership, which widens `lexon_auth`; aggregates and cursor logic live in TypeScript.              |
| C   | Plain Drizzle queries on the `lexon_auth` connection.                                                                                                                                                          | No new grants, but nothing in the database limits which columns are read; does not satisfy the brief's "narrow path".                                                     |

**Decision: A.** Reads do not widen `lexon_app` or `lexon_auth` table grants;
they add only `EXECUTE` on six functions to `lexon_auth`.

## 4. Backend design

### 4.1 Read functions (migration `0040_platform_console.sql`)

Read functions are `STABLE`; `lexon_platform_lock_enabled_admins()` and the invitation write functions are `VOLATILE` (owner fix, plan Task 2). All are `LANGUAGE sql` (or plpgsql for the invitation writes) `SECURITY DEFINER SET search_path=pg_catalog,auth,pg_temp`,
`REVOKE ALL ON FUNCTION ... FROM PUBLIC`, `GRANT EXECUTE ... TO lexon_auth`.
List functions take filters, `page_size int` (10, 20, or 50; validated by
Zod and checked again in SQL) and `page_offset int` (`(page - 1) * pageSize`),
and return each row with `count(*) OVER () AS total` so the page and the
total come from one statement and one snapshot. A page past the end returns
no rows; the service then runs the function's `_total` companion (same
filters, `count(*)` only) so `total` is still correct (§9 notes).

| Function                                                                                              | Returns (columns)                                                                                                       | Order                                   |
| ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| `lexon_platform_accounts(q text, statuses text[], two_factor bool[], page_size int, page_offset int)` | `id, name, email, status, two_factor_enabled, is_platform_administrator, team_count, created_at, last_active_at, total` | `created_at DESC, id DESC`              |
| `lexon_platform_account(uid uuid)`                                                                    | summary columns + `email_verified, active_session_count`                                                                | single row or none                      |
| `lexon_platform_account_teams(uid uuid)`                                                              | `organization_id, name, slug, role` for `kind='team' AND state='active'`                                                | `name, id` (unpaged; small per account) |
| `lexon_platform_organizations(q text, states text[], page_size int, page_offset int)`                 | `id, name, slug, state, member_count, owner_email, created_at, total` for `kind='team'`                                 | `created_at DESC, id DESC`              |
| `lexon_platform_organization(oid uuid)`                                                               | summary columns + `require2fa` (active) or the owner invitation `id, status, expires_at` (provisioning)                 | single row or none                      |
| `lexon_platform_members(oid uuid, page_size int, page_offset int)`                                    | `user_id, name, email, role, joined_at, total`                                                                          | `member.created_at ASC, user_id ASC`    |
| `lexon_platform_account_invitations(q text, statuses text[], page_size int, page_offset int)`         | `id, email, name, status, invited_by_name, sent_at, expires_at, total` for pending and expired only                     | `sent_at DESC, id DESC`                 |
| `lexon_platform_lock_enabled_admins()`                                                                | ids of enabled platform administrators, `FOR UPDATE`                                                                    | —                                       |

Derivations (all in SQL):

- `status`: `banned` → `disabled`; else `NOT email_verified` → `unverified`; else `active`.
- Facets: `statuses` is the selected subset of `active|unverified|disabled`; `two_factor` the selected subset of `{true,false}`; `NULL` means no filter. Facet values within one facet are OR; facets and search are AND.
- `team_count`: `member` rows in `kind='team' AND state='active'` organizations.
- `active_session_count`: sessions with `expires_at > now()` and (`hard_expires_at IS NULL OR hard_expires_at > now()`).
- `last_active_at`: `max(session.updated_at)` over the user's sessions (§4.4).
- `owner_email`: active → email of the owner member with the earliest `member.created_at`; provisioning → the owner invitation's email.
- Invitation `status`: `pending` while `expires_at > now()`, else `expired`; accepted and cancelled invitations are never listed.
- Search: `lower(col) LIKE '%' || lower(q) || '%' ESCAPE '\'` on name or email (organizations: name or slug; invitations: email or name), with `%`, `_`, `\` escaped in TypeScript.
- `is_platform_administrator`: `role = 'admin'` (the Better Auth admin role Lexon gives platform administrators; owner decision 2026-11-21).

Indexes (same migration):

- `user_created_at_id_idx ON auth."user"(created_at DESC, id DESC)`
- `user_name_trgm_idx`, `user_email_trgm_idx`: `GIN (lower(name) gin_trgm_ops)`, `GIN (lower(email) gin_trgm_ops)`
- `organization_team_created_idx ON auth.organization(created_at DESC, id DESC) WHERE kind='team'`
- `organization_name_trgm_idx`, `organization_slug_trgm_idx` (GIN trigram on `lower(...)`)
- `member_org_created_idx ON auth.member(organization_id, created_at, user_id)`; `member_user_idx ON auth.member(user_id)` if not already present
- `session_user_expires_idx ON auth.session(user_id, expires_at)` if not already present
- account invitation indexes: §4.7

**Why offset paging is acceptable here.** The brief fixes numbered pages with
a total. With at most 50 rows per page, an offset of page N costs reading
`N × pageSize` index entries, and `count(*) OVER ()` reads the whole filtered
set once. At 10,000 accounts that is bounded and measured by the scale check
(§5); the check fails if either plan uses a sequential scan on an unfiltered
first page. Keyset paging stays for chats and feeds (`PaginationSchema`).

### 4.2 Routes, guards, schemas

New `PlatformConsoleModule` (backend `modules/platform-console`), controllers
under `/api/platform`, all `@PlatformRoute()` (anonymous 401, non-admin 403
`ORG_FORBIDDEN`, admin without 2FA 403 `ORG_FORBIDDEN`, as today). Reads run in
a new `OrganizationAuthPort.platformRead` that re-checks the platform policy
like `platformTransaction` but does **not** require re-authentication (my
call: reads are not sensitive actions; mutations keep re-authentication as
today). Reads and mutations use the authenticated API rate limit.

**Numbered-page contract** (`shared/src/numbered-page.ts`, for every data
table, not only this slice; the cursor `PaginationSchema` stays for feeds):

```ts
export const PageSizeSchema = z.union([
  z.literal(10),
  z.literal(20),
  z.literal(50),
]);
export const NumberedPageQuerySchema = z.strictObject({
  page: z.coerce.number().int().min(1).max(10_000).default(1),
  pageSize: z.coerce.number().pipe(PageSizeSchema).default(20),
});
export const numberedPageSchema = <T extends z.ZodType>(item: T) =>
  z.strictObject({
    items: z.array(item),
    page: z.number().int().min(1),
    pageSize: PageSizeSchema,
    total: z.number().int().nonnegative(),
  });
// Repeated facet parameter: ?status=active&status=disabled, or a single value.
export const facetSchema = <T extends z.ZodEnum>(values: T) =>
  z
    .preprocess(
      (v) => (v === undefined ? undefined : [v].flat()),
      z.array(values).min(1).max(values.options.length).optional(),
    )
    .transform((v) => (v ? [...new Set(v)] : undefined));
```

Default page size 20 (my call; the prototype footer shows 10 for its small
fixture). `page` beyond the last page returns `items: []` with the true
`total`; the UI then moves to the last page. The `max(10_000)` bound is a
guard against absurd offsets (my call).

### 4.3 Actions and refusals (API-enforced)

All run inside `platformTransaction` (platform role, 2FA, re-auth), so the
refusal checks and the action share one transaction.

1. **Self refusal** (disable `true`, sessions revoke): `targetUserId === identity.userId`
   → 409 `PLATFORM_SELF_ACTION`. Enabling yourself is
   unreachable (a disabled admin cannot sign in) and is not special-cased.
   Better Auth's own `YOU_CANNOT_BAN_YOURSELF` stays as a second line.
2. **Last enabled platform administrator** (disable `true`): in the
   transaction, `SELECT ... FROM auth."user" WHERE role='admin' AND NOT coalesce(banned,false) FOR UPDATE`
   via a new `SECURITY DEFINER` function `lexon_platform_lock_enabled_admins()`
   returning the ids; if the target is the only one → 409 `PLATFORM_LAST_ADMINISTRATOR`. The row lock serialises two concurrent
   disables of the last two admins (tested with two parallel transactions).
   With the self refusal in place this can only happen when another admin is
   targeted while the actor is not enabled-admin-countable, i.e. defence in
   depth; it is still enforced and tested.
3. **Sign out everywhere:** Better Auth admin `revokeUserSessions({ body: { userId } })`
   (`internalAdapter.deleteUserSessions`). Bearer tokens are session tokens
   (the bearer plugin converts `Authorization: Bearer` into the session cookie),
   so deleting session rows revokes them. Lexon's `RevalidationCache` TTL is
   1 s, so other devices fail at their next request after at most 1 s (test:
   a bearer request and a cookie request for the target both get 401 after
   revoke). Per-target limit: new `AuthLimiter` action `platform-session-revoke`,
   5 per target account per 600 s → 429 `AUTH_RATE_LIMITED`. Audit
   `platform.user_sessions_revoked.v1`.
4. **Resend verification email:** read `email_verified` via
   `lexon_platform_account`; verified → 409 `PLATFORM_ALREADY_VERIFIED`;
   consume the target's existing `verification-resend` **account** bucket
   (shared with the user's own resends, so the admin cannot exceed the user's
   limit) → 429 `AUTH_RATE_LIMITED`; then call `auth.api.sendVerificationEmail({ body: { email } })`
   **without** the admin's headers. With headers Better Auth 1.7.14 compares the
   session user's email and throws `EMAIL_MISMATCH`; without a session it takes
   the anonymous branch (constant-time 500 ms floor, sends only to unverified
   users). The existing verification email template and expiry are unchanged.
   Audit `platform.verification_email_resent.v1`.
5. **Disable** keeps today's behaviour (`banUser` deletes the user's sessions).

### 4.4 Last active

`lastActiveAt` is the latest session activity: `max(session.updated_at)` over
the user's session rows, `null` when there are none (owner decision,
2026-11-21). It therefore becomes `null` after Sign out everywhere or Disable,
and when expired sessions are pruned; that is accepted. No new table.

### 4.4a Error codes

`PLATFORM_SELF_ACTION`, `PLATFORM_LAST_ADMINISTRATOR`,
`PLATFORM_ALREADY_VERIFIED`, `PLATFORM_INVITATION_CONFLICT`. Unknown

### 4.6 Logging and privacy

`query` is redacted from request logs and OTel span attributes (extend the
existing redaction list; test asserts a search term never appears in captured
logs/spans). No session IP, user agent, or device name is selected by any
function.

### 4.7 Account invitations (decision 9)

**Entity.** Better Auth's organization `invitation` table is bound to an
organization, so account invitations get a Lexon-owned table in schema
`auth` (migration 0040):

```
auth.lexon_account_invitation(
  id uuid PK default gen_random_uuid(),
  email text NOT NULL,              -- stored lower-cased and trimmed
  name text NULL,
  token_digest text NOT NULL UNIQUE, -- sha256 of the link token; the token is never stored
  invited_by uuid NOT NULL REFERENCES auth."user"(id),
  status text NOT NULL CHECK (status IN ('pending','accepted','cancelled')),
  sent_at timestamptz NOT NULL,
  expires_at timestamptz NOT NULL,  -- sent_at + 7 days
  accepted_user_id uuid NULL REFERENCES auth."user"(id),
  created_at timestamptz NOT NULL default now(),
  updated_at timestamptz NOT NULL default now()
)
UNIQUE INDEX ... (email) WHERE status = 'pending'
INDEX ... (sent_at DESC, id DESC) WHERE status = 'pending'
GIN trigram indexes on lower(email), lower(coalesce(name,''))
```

`expired` is derived (`pending` and `expires_at <= now()`), never stored, so
no job is needed. `lexon_app` gets no grant; `lexon_auth` reaches it only
through `SECURITY DEFINER` functions:
`lexon_create_account_invitation`, `lexon_resend_account_invitation`,
`lexon_cancel_account_invitation`, `lexon_account_invitation_signup_facts(digest)`,
`lexon_accept_account_invitation(digest, user_id)`.

**Create** (`POST`, inside `platformTransaction`, so 2FA and re-auth apply):

1. `pg_advisory_xact_lock(hashtext('account-invitation:' || lower(email)))` serialises concurrent invites of one address.
2. If `auth.user` has that email (case-insensitive), or a **pending, unexpired** invitation exists → 409 with one field error on `email`: "This address already has a Lexon account or a pending invitation." The same code, status, message, and timing path for both cases, so the response says nothing the administrator cannot already see in the two lists.
3. A pending but **expired** invitation for the address is set to `cancelled` (superseded) in the same transaction.
4. Insert with a fresh 32-byte random token (digest stored), `sent_at = now()`, `expires_at = now() + 7 days`.
5. Send the invitation email through the existing outbox/email path, with the link `/sign-up?accountInvitation=<token>`. The email carries no organization content.
6. Audit `platform.account_invitation_created.v1`.
7. 201 with the `AccountInvitation` row.

Per-administrator limit: new `AuthLimiter` action `platform-account-invite`,
20 per administrator per hour (my call) → 429 `AUTH_RATE_LIMITED`.

**Resend:** pending (expired or not) → new token and digest, `sent_at = now()`,
`expires_at = now() + 7 days`, the old link stops working; email sent; audit
`platform.account_invitation_resent.v1`. Accepted, cancelled, or unknown → 404. Per-invitation limit: new action `platform-account-invite-resend`,
3 per invitation per 600 s (mirrors `verification-resend`).

**Cancel:** pending → `cancelled`; audit `platform.account_invitation_cancelled.v1`.
Already accepted, cancelled, or unknown → 404.

**Acceptance into a Personal workspace, with public sign-up off.** Lexon does
not use Better Auth's `emailAndPassword.disableSignUp` (it would also block
invited and setup sign-ups); it keeps Better Auth sign-up enabled and gates
`/sign-up/email` in `SignupPolicy` (`signup-policy.ts`) when
`AUTH_OPEN_SIGNUP=false`, accepting today an organization `invitationId` or an
admin `setupToken`. F4.3 adds a third proof:

- `SignUpInput` gains `accountInvitationToken: FlowTokenSchema.optional()` (**contract change**, `shared/src/auth.ts`).
- `SignupPolicy.authorize` digests the token, reads `lexon_account_invitation_signup_facts`, and allows sign-up only when the invitation is `pending`, unexpired, and its email equals the sign-up email (case-insensitive).
- After Better Auth creates the user, the existing sign-up completion hook calls `lexon_accept_account_invitation(digest, user_id)` in the same auth transaction: it re-checks pending and unexpired with `FOR UPDATE`, sets `accepted`, `accepted_user_id`. If it returns false (cancelled or resent in between), the sign-up transaction is rolled back and the user sees the existing invalid-link state.
- The Personal workspace is created exactly as for any sign-up today (0004); no team membership is created. Teams invite them separately (F1).
- **The email is verified on acceptance** (owner decision 2026-11-21): the link was delivered to that address. `lexon_accept_account_invitation` sets `auth.user.email_verified = true` in the same transaction, and the sign-up sends no verification email: `SignupPolicy` sets a request-scoped flag when the invitation proof was used, and the `sendVerificationEmail` callback (`auth-factory.ts:107`) skips enqueueing for it. Tests: no verification email in the outbox; status Active right after sign-up.
- The token is single-use (acceptance sets `accepted`; a second use is refused), stored only as a SHA-256 digest, and expires 7 days after it was sent.
- Audit `platform.account_invitation_accepted.v1` (actor = the new user, subject = the new user, metadata `{ invitationId }`).
- UI: the existing sign-up page reads `?accountInvitation=`, prefills and locks the email, prefills the name, and on an unusable token shows the existing `invite-invalid` auth state (prototype). No new capture id (my call; revision 16 draws no acceptance screen).
