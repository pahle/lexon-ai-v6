## Planning findings (need the owner's ruling before the task that uses them)

These came out of re-reading the code at `f25ec1c7` while writing the plan. They are logged in spec §8 as pending. The executor does not decide them.

- **P1 (task 1, GHSA-45rx proof).** The spec's propagator test asserts the OTel default (`tracecontext,baggage`). The code does not use the default: `backend/src/infrastructure/telemetry/ai-telemetry.ts:154` sets `textMapPropagator: noPropagation` (lines 160–164: injects nothing, extract returns `context.active()`). **Proposed:** the unit test asserts that the SDK is built with `noPropagation`, that `extract` with `uber-trace-id: %`, `traceparent` and `baggage` headers returns the same context as `context.active()`, and that `inject` writes no header. The integration test (`uber-trace-id: %` → normal status, second request succeeds) stays as written. This is stricter than the spec and weakens nothing.
- **P2 (task 7, item 8).** The spec says "the route family is decided by the existing route classification in the filter". `backend/src/modules/platform/error.filter.ts` has no route classification. It classifies by error type, and every outage (57P01/57P03/`ECONNREFUSED`/connect timeout) maps to 503 `AUTH_UNAVAILABLE` (lines 85–94, 161–166). **Proposed:** add `isChatRoute(path: string): boolean` in the filter, true for paths under `/api/chats` and `/api/runs`. Outages on those paths map to 503 `SERVICE_UNAVAILABLE`, and every other path keeps `AUTH_UNAVAILABLE`. An `IdentityError` passes through unchanged on every path, so the tenant guard's own `AUTH_UNAVAILABLE` (identity database) still reaches chat clients.
- **P3 (task 11, amendment 7).** The logger never serializes headers: `logging.ts:61–64` emits `req: { id, method }` only, and `streamWrite` (111–152) re-filters to an allowlist. No redaction entry is needed. The plan keeps the required test (a logged request carries neither value) and adds no redaction path. This needs no ruling unless the owner wants the two header paths added to `redact.paths` anyway.

## Review Focus

Failure modes the spec implies but no listed test exercised. Each line has a test in its owning task.

1. **A 304 reaching an old client path.** `chat-client.ts` `call` throws on any non-`ok` response, and a 304 is not `ok`. Any `ChatClient.get` caller that sends a tag must get `{ notModified: true }`, never a thrown `chatClientError`. Test in task 10 (client unit).
2. **A stale tag after a branch switch or a chat switch.** `use-tree-polling` must drop its stored ETag when `chatId` changes, so chat B is never asked `If-None-Match: <tag of A>`. Test in task 10.
3. **`If-None-Match` lists and `*`.** `W/"a", W/"b"` must match when one entry matches, and `*` matches any live chat but never turns a 404 into a 304. Test in task 10 (unit of the matcher plus the foreign-actor test).
4. **Neutral 503 never masks an identity outage on chat routes.** An `IdentityError('AUTH_UNAVAILABLE', 503)` thrown by the tenant guard on `/api/chats/...` must still return `AUTH_UNAVAILABLE`, so the client's sign-in fallback keeps working. Test in task 7 (filter unit).
5. **`pgArray` rejection is a safe 400, not a 500 with SQL text.** A facet value outside the enum must fail before SQL is built, and the error body must not echo the value. Test in task 9.
